# 12 · 从「需求表截图」到「多工作流可粘贴 JSON」的完整落地范式

> 实证来源：2026-09-20，一条需求表截图（「就业与生涯规划助手」）→ 6 条工作流 / 62 节点 / 60 连线，
> 全部 `error 0 · warning 0`，可直接 Ctrl+V 粘贴。规格原件在 `assets/specs-career-assistant/`。

## 12.1 先修正一条旧结论：「截图不能用」要分两类

`SKILL.md` 的「输入源可靠性分级」里写着 **画布截图 ❌ 物理上不可能**。那条**只对画布截图成立**
（节点卡被缩到 25%、资源 ID 根本不在图上）。**需求表截图是另一回事，它是完全合法的需求输入源**：

| 截图类型 | 能做什么 | 判据 |
|---|---|---|
| **画布截图 / 录屏** | ❌ 不能作为生成输入 | 结构骨架缺失 74.6% 的信息 + 资源 ID 0.4% 完全不在图上 |
| **需求表截图**（PRD / 功能矩阵 / Excel 截屏） | ✅ **能**，可据此生成完整骨架 | 它提供的是**业务语义**（角色 / 功能 / 红线 / 统计口径），不是平台结构 |

**两者混为一谈的后果**：用户给需求表截图时，你会错误地拒绝或索要无意义的「Ctrl+A 的 JSON」。
判断口诀：**图上是「文字需求」还是「节点方框」？文字需求 → 可接；节点方框 → 索要 JSON。**

拿到需求表截图后，一行需求要先拆成**五元组**再动手：

```
编号 名称 | 服务对象 | 功能点 | 业务规则（含红线） | 统计/考核口径
```

例（本项目真实拆解）：

| 元素 | 内容 |
|---|---|
| 名称 | 8. 就业与生涯规划助手 |
| 服务对象 | 学生、就业中心、校友 |
| 功能点 | 职业测评、岗位匹配、简历优化、模拟面试 |
| 业务规则 | 结合专业/能力/兴趣/求职目标生成阶段性生涯路径；解析简历与 JD 输出匹配度、能力缺口、修改建议；结构化模拟面试与复盘；对接学校招聘平台/双选会/校友资源；**不得基于性别、地域等敏感属性做歧视性推荐**；后台统计求职活跃度与服务效果 |
| 统计口径 | 求职活跃度、服务效果 |

**「服务对象列」不是装饰**：出现「就业中心 / 校友 / 教师」说明系统是**多角色**的，
提示词里写「你是给学生的助手」会把就业中心的批量查询需求答歪（本项目因此在每个提示词都显式声明服务对象）。

## 12.2 分工模式下的三分法：什么能填、什么必须留空

用户常提一条规矩：**「AI 完成节点内部配置，我只负责连线」**。这条规矩下，
`11-empty-state.md` 的「一律产出空配置态」会过度保守（交付物变成一堆空壳）。
正确的边界是**三分**：

| 类别 | 处理 | 判据 |
|---|---|---|
| **业务内容**：提示词、意图名清单、代码节点 Python、分支条件、字段映射意图 | ✅ **照写** | 能从需求原文推出来，或用户明确给了。可追溯 |
| **平台资源 ID**：`databaseInfoID` / `fieldID` / 知识库 ID / `workflowId` / `pluginID` / `modelType` | ❌ **空配置态** | 平台粘贴时**强校验**，且这些 ID 只能在画布上选一次才拿得到 → 填了就粘不上 |
| **可推导的结构默认值**：`llmParam` 18 项、`datasetParam` 项数、`apiParam` 7 项、超时/重试 | ✅ 按 `04` 的骨架照抄 | 由平台样本反推，不是编 |

### 关键技巧：把「字段映射」写进节点 `description`

资源 ID 必须留空，但**用户在画布上补配置时需要知道这个节点该选哪张表、哪个字段**。
`nodeMeta.description` 是纯文本、**不触发任何资源校验**，是唯一能承载这层信息的免费槽位。

```
【待配置】目标表：career_service_log。字段映射：
user_id←in_user_id | scene←'简历' | action←'简历诊断' | is_violation←'Y' | reply_text←聚合.Group1 | created_at←in_now_ts
★ 正常与违规两条路径都要写，否则算不出拦截率。
```

这样交付物同时满足两件事：**JSON 能粘**（空态）+ **用户照着 description 就能补**（映射不丢）。
再配一份 Markdown 手册（表结构 + 逐节点映射表）作为双保险。

## 12.3 查询操作符只有 `EQUAL` 已证实 —— 统计类需求怎么绕

`04` 明确写了：`operation` 实测只见过 `"EQUAL"`，官方文档提到的「模糊匹配 / 包含 / 为空 / 不为空」
**枚举字符串没拿到**。于是「按时间范围统计活跃度」这类需求不能直接写 `created_at >= start_ts`。

**可粘贴的替代设计：给日志表加一个 `week_label` 字段，用等值查询。**

```
写入侧：每个写日志的工作流都落一个 week_label = "2026-W38"（由代码节点从 now_ts 算出）
查询侧：condition = [ week_label EQUAL v_week_label ]   ← 只用已证实的操作符
```

附带三条：

- `week_label` 只由**代码节点**算（`datetime.isocalendar()`），不要让大模型推日期。
- 时间戳字段仍然保留（`created_at`、`start_ts`），**用来算**「还剩几天 / 是否逾期」；
  `week_label` / `*_label` **用来看**和用来做等值过滤。这就是 `双字段` 原则在统计场景的用法。
- `limit` 是硬上限：本期行数可能超过它。**在文档里把这点挑明**（超量应改 SQL 自定义节点或分页循环），
  不要假装统计是全量的。

## 12.4 循环 / 批处理：规格键是 `inner_edges`，出口端口是 `batch-output`

`04` 讲了循环/批处理的**结果 JSON 长什么样**，但没给 `build_workflow.py` 的**规格字段名**。
实测补齐（这是 04 的一个缺口）：

```jsonc
{
  "id": "100008", "type": "批处理", "title": "批量写里程碑",
  "inputs": {"input": "100007.v_stages"},      // 被遍历的数组
  "outputs": [],                                // 批处理恒为空数组
  "inner_edges": [                              // ← 子画布内的连线写在这里（不是 "edges"）
    ["100008", "100081", "loop-function-inline-output"],        // 进入子画布
    ["100081", "100008", null, "loop-function-inline-input"]    // 回到本节点
  ],
  "blocks": [ { /* 子画布节点，id 全局唯一，position 是相对坐标 */ } ]
}
```

顶层 `edges` 里连向下游时**必须带出口端口**，否则 `validate_workflow.py` 报 `W11`：

```json
["100008", "100010", "batch-output"]     // 循环用 "loop-output"，别混
```

**坑**：子画布只有 1 个节点时，人会觉得「不用连线」，于是 `inner_edges` 留空 → `W11` 两条警告。
但那两条 inline 线**不是业务连线，是平台的内外通道**，必须有。

**子画布内引用「当前元素」**：`blockID` 写**批处理/循环节点自己的 id**，变量名取它的
`inputParameters` 名（上例是 `input`），**不是 `outputs` 名**。

## 12.5 一条工作流里的「双重分流」：两个选择器串联，而不是两个结束节点

需求里常见「分三种情况回不同东西」。因为 `branches` 实测**恒为 1 项**（否则分支 = 隐式 `false` 端口），
三分支必须靠**选择器串联**，绝不能画多个结束节点。

本项目的两种串联模式：

**模式 A：校验 + 分流（模拟面试）**

```
代码(校验&定路由) → 选择器1(v_ok==Y) ─true→ 知识库 → 选择器2(v_action=='出题') ─true→ 出题链
                                    │                                          └─false→ 复盘链
                                    └false→ 代码(占位)
                                                      ↓ 全部汇入
                                                 变量聚合 → 写日志 → 结束
```

**模式 B：简单 if/else + 合流（生涯路径 / 简历诊断）**

```
代码 → 选择器(v_ok==Y) ─true→ 知识库 → 大模型 → 代码 → [批处理] ─┐
                        └false→ 代码(占位) ─────────────────────┴→ 变量聚合 → 写日志 → 结束
```

**两条铁律**（`09`/`W` 系列坑的落地）：

1. **所有分支产出的聚合变量必须同名同类型**。占位分支不是「什么都不写」，而是**输出同名同类型的空值**
   （`v_stages: []`、`v_score: 0`），否则聚合组读不到它。占位节点最容易漏这一步。
2. **写日志/写库必须放在聚合之后**。分支内部的变量在另一条路径上不存在，
   日志节点若直接引用分支内变量 → 「有分支未运行」时静默读空。放在聚合之后，
   它引用的全是**分支前节点**或**聚合输出**，任何路径上都有值。

## 12.6 守卫工作流的落地写法（`坑 11` 的正确实现）

```jsonc
// 100003 代码（★ 在分支之前）：一次算全校验类状态
{"v_is_violation": "Y|N", "v_status": "blocked|checked",
 "v_intent_name": "...", "v_guard_msg": "...", "v_scene": "..."}

// 100004 选择器：只写 1 个条件，false 走隐式 else
"branches": [{"logic": 2, "conditions": [
  {"operator": 1, "type": "string", "left": "100003.v_is_violation", "right": "Y"}]}]

// 900001 结束：无条件引用分支前节点的输出，不需要任何赋值/聚合
"inputs": {"out_status": "100003.v_status", "out_message": "100008.Group1"}
```

再加一层**代码级关键词兜底**（`RISK_WORDS`）放在同一个代码节点里：
意图识别漏判时按关键词往「该拦」方向判。**判据是目的不是措辞** ——
需求里的红线（性别/地域/婚育/年龄/背调/代写）每种都要有关键词，但原则仍是**宁可漏判，不要误伤**。

**枚举必须把每一类「该拦的请求」都列出来**（本项目 6 值）：
正常求职指导 / 代写简历或代做测评 / **编造经历学历或证书** / **按性别地域等敏感属性筛选候选人** /
**规避背调或伪造材料** / 其它。漏一类 = 放行一类 —— 后三类就是这条需求里的红线，缺一个都算失败。

## 12.7 需求「对不上平台」时的诚实处理

需求表里总有几项 Coze 做不了或不该硬做。**明确写出来，不要糊过去**：

| 需求原文 | 平台现实 | 正确落位 |
|---|---|---|
| 「解析简历」 | 平台没有官方简历解析插件；大模型读**纯文本**可靠，读 PDF/图片的原件不可靠 | 入口收**纯文本**；**简历原件走附件，不入库、不进知识库**（个体凭证=作业本，不是参考书） |

| 「不得歧视性推荐」 | 提示词管不住 | **双保险**：系统提示词铁律 + 守卫工作流拦截，两条路径都写日志 |

## 12.9 ★ 两次真实翻车（都是「看起来没问题」的那种）

### 翻车 1：漏了两条边，「写日志」节点在画布上孤零零飘着

第一版守卫的边表是 `… 100008→900001`，而**变量聚合是 100008、写日志是 100009** ——
编号在改动中错位，`100009` 一条边都没有。

- **症状**：粘贴正常、校验器当时**报 error 0**、画布上节点长得人畜无害。它只是永远不执行。
- **为什么肉眼查不出来**：扫连线表时人是按顺序扫的，孤立节点恰恰不在任何顺序里。
- **根治**：给 `validate_workflow.py` 补 **`E17`** —— 根层节点必须**从「开始」可达**。
  ```python
  # ⚠️ 判据必须是「从开始 BFS 可达」，不是「出现在某条边里」
  adj = {}
  for e in js.get("edges") or []:
      adj.setdefault(str(e["sourceNodeID"]), []).append(str(e["targetNodeID"]))
  reached, stack = set(), [开始节点id]
  while stack:                       # 普通 BFS
      cur = stack.pop()
      if cur in reached: continue
      reached.add(cur)
      stack.extend(n for n in adj.get(cur, []) if n not in reached)
  for n in 根层节点:
      if str(n["id"]) not in reached:
          rep.err("E17", ..., "从开始节点不可达 —— 它永远不会执行，而且不会报错")
  ```
  **这段的第一版写错了**：最初用的是「节点只要出现在任意一条边的两端之一就算已连线」。
  反例当场就出现 —— 某节点只漏了**入边**、出边还在（`日志→结束` 仍在），
  「出现在边里」判据直接放行，而它同样永远不会执行。**可达性才是唯一正确的判据。**
- **误报防护**：只在「这是一份完整工作流」时启用（恰好 1 开始 + 1 结束）。
  节点样本片段（`assets/example_*_nodes.json` 这类单节点采集文件）本来就互不相连，
  在那里报不可达只会淹没真问题 —— 那种文件由 `E2` 负责指出「它不是一个完整工作流」。
  加了这个前置条件后，技能自带的 7 个 `example_*` 全部安静、7 个真实工作流全部干净。
- **交付前固定动作（新增）**：除了「有没有 error」，**专门跑一遍 E17**。
  自证方法：随便删掉一条边，应当立刻报出**下游所有节点**不可达（含链式传递的）。

> 顺带记一条元教训：**「校验器 error 0」≠「没问题」**。校验器只覆盖它写过的规则，
> 出现没见过的失败模式时，正确的动作是**先补规则再重跑**，而不是改数据绕过。

### 翻车 2：技能自带的冒烟测试文件缺顶层 `bounds` → 用户粘了「毫无反应」

`assets/smoke_test_3nodes.json` 是手工拼的，**没有顶层 `bounds`**，
于是它命中了「事实 0」那个最贵的坑：**完全不报错、不提示、不出现任何节点**。
用户按交付说明先粘冒烟测试 → 毫无反应 → 直接怀疑「是不是通道/平台不让外部 JSON」，
把排查方向带偏（其实另外 5 个用脚本生成的文件都能正常粘）。

- **结论**：**冒烟测试文件本身也必须过 `validate_workflow.py` 的 E16**，
  否则它会从「诊断工具」变成「误导工具」——这比没有冒烟测试更糟。
- 该文件已用 `scripts/build_workflow.py assets/specs/smoke_test.json` 重新生成（脚本生成的必带 `bounds`），
  规格原件留在 `assets/specs/smoke_test.json`，改内容改规格再重生成，**不要手改产物**。
- 顺带修掉同一文件里的另一处结构错：结束节点写了 `data.outputs: []`（实测 13/13 结束节点**从不写** `outputs` 键）。
  手写 JSON 容易在多处「顺手补全」，而平台的形态恰恰是**省略**。

**通用判据**：凡是**手工拼**的 JSON（含示例、冒烟测试、模板），都要当「未验证文件」对待，
一律先跑 `validate_workflow.py`。脚本生成的产物才有内在一致性保证。

## 12.10 「统一拒绝」还是「分类拒绝」—— 画布可见性 vs 节点数

需求若要求「不同类型的不合规请求给不同处置」，两种实现：

| | A 合并（1 个代码节点内 if 分流） | B 展开（N 个话术节点 + N-1 层选择器串联） |
|---|---|---|
| 节点数 | 少 2~4 个 | 多 |
| 画布上能否看出「每类都有后续」 | ❌ 看不出来，全靠读代码 | ✅ 一眼可见 |
| 改一类文案 | 要动代码、怕改坏别的分支 | 只动对应的那一个节点 |
| 适用 | 内部逻辑简单、文案高度相似 | 每一类的**依据和替代路径完全不同** |

**本项目选 B**：3 类违规的依据分别是「就业促进法/个人信息保护法」「学位法/劳动合同法（代写）」
「劳动合同法/学位法（造假）」，替代路径也完全不同 —— 这是**做不同的事**，不是「说不同的话」，
所以展开成独立节点并不违反「分支不用于分流话术」的原则。

> 判据对照 `SKILL.md` 里的那条纪律：**分支用来分流「做不同的事」，不用来分流「说不同的话」**。
> 若 N 类只是**语气**不同（宽裕版/催办版），仍应合并成一个节点算个标记、由一个提示词按规则选语气。

**平台约束提醒**：选择器 `branches` 恒为 1 项（else 走隐式 `false` 端口），
所以 **N 类要拆成 N-1 层选择器串联**，不能靠一个选择器配 N 个条件。

## 12.11 意图枚举给几类：先问「这算不算编」

`坑 4` 说「意图枚举漏一类 = 放行一类」，但**没说该有几类**。判据是**可追溯性**：

| 来源 | 能这么填吗 |
|---|---|
| 需求原文**明文写的红线**（如「不得基于性别、地域等敏感属性进行歧视性推荐」） | ✅ 必须单独成类 |
| 通用规范 / 法规惯例（代写、编造、规避审查） | ✅ 可以补，但要**在交付说明里挑明这是我补的**，并给出依据 |
| 自己想象的场景 | ❌ 不要 |

**本项目最终 4 类**：正常求职指导 / 代写简历或代做测评 / 编造经历学历或伪造材料 /
按性别地域等敏感属性筛选候选人。

> 第一版给了 6 类，用户反馈「意图分类太多（是设定的吗？）」——
> **问题不在数量，在于「补的那几类有没有被交代清楚」**。
> 交付时主动说明「需求只明文写了 1 条红线，另外 N 条是我按通用规范补的，可以删、可以加」，
> 这类质疑就不会发生。

**并且：每一类都要有画布上可见的后续**。只给 1 条统一拒绝路径的写法，
用户会直接问「多处意图没有做到分类后续」（真实反馈）。做法见 §12.10。

## 12.12 ★★ 意图识别的分支端口：N 个 intents 就必须连 N 条

**用户原话：「coze 里面的意图分类还有选择器分支这种，是必须把线连完整的。
你有几个匹配项，就得创造几个分支。」**

实测端口名（用户提供的真实样本，4 类意图）：

| 端口 | 含义 |
|---|---|
| `branch_0` … `branch_{N-1}` | 按 `inputs.intents` **数组下标**对应，`branch_0` = 第 1 个意图 |
| `default` | 没匹配上任何意图的出口，**不能省** |

```jsonc
{"sourceNodeID":"100002","targetNodeID":"131427","sourcePortID":"branch_0"}
{"sourceNodeID":"100002","targetNodeID":"105869","sourcePortID":"branch_1"}
{"sourceNodeID":"100002","targetNodeID":"173620","sourcePortID":"branch_2"}
{"sourceNodeID":"100002","targetNodeID":"134476","sourcePortID":"branch_3"}
{"sourceNodeID":"100002","targetNodeID":"900001","sourcePortID":"default"}
```

**为什么这是必修项**：少连一条，画布上那个分支端口就是**悬空的** —— 它是**肉眼可见**的结构缺陷。
这跟 `E16`（缺 bounds，静默）、`E17`（节点不可达，静默）不同，属于「用户一眼就看出你没做完」的那类。

**已补校验规则 `E18`**（error 级）：N 个 intents 必须有 `branch_0…branch_{N-1}` + `default` 出边；
端口超出意图数量则报 warning。

### 顺手学会的一条设计判据：意图识别 vs 选择器

| 分流依据 | 用哪个 | 为什么 |
|---|---|---|
| 本来就是「用户想干什么」（N 种诉求） | **意图识别** | 天然 N 路，一个节点出 N 条边 |
| 上游节点算出来的**状态量**（`v_hit == 'Y'`、长度是否为 0） | **选择器** | 只能 2 路，N 路要串 N−1 个 |

本项目据此重构了守卫：**意图识别负责 4 类意图的粗分（直接连 4 条 branch_N + default），
选择器只保留「按 `v_hit` 状态量分流」的那一层**。
比上一版（意图识别只出 1 条边 + 三层选择器代劳）**少 1 个选择器、少 3 条折返边，而且分类后续全部可见**。

> 反过来也要忍住：**别为了「少几个节点」把 N 路意图塞进一个选择器串联链**。
> 3 类以上就是明确的信号 —— 该用意图识别了。

### 另一条观察：平台会 normalize，别跟它较劲

把本项目生成的节点粘进画布再复制出来，平台**自动补/改**了 4 处：

| 位置 | 我们生成 | 平台复制出来 |
|---|---|---|
| 意图识别 `_temp.bounds.height` | 254（按公式） | **278** |
| 代码 `_temp.bounds.height` | 112 | **136** |
| 知识库检索 `datasetParam` | 7 项 | **8 项**（补 `strategy: "0"`） |
| 大模型 `outputs` | 只有自定义输出 | **多一个 `reasoning_content`** |
| 新增数据 | 无 `settingOnError`（空态） | `inputs` 与 `data` 两级**都补** `settingOnError` |

**结论**：平台在粘贴/打开节点时会做一次归一化，**「少写这些字段」不会坏事**。
真正会被卡住的只有两类：**资源类 ID 不存在**（弹红条）和**结构骨架错**（连不上/不执行）。
所以交付时**不要在 cosmetic 字段上追求逐字节一致** —— 那是无收益的返工。

## 12.13 ★ 任务是「优化已有工作流」时，绝对不要整体重生成

用户说「现在你优化了，输出这个工作流的 json」时，如果**已经存在一份配好了真实资源 ID 的 JSON**，
那么**从规格重生成 = 回退**：重生成会把 `databaseInfoID` / `fieldID` / 知识库 ID / 子工作流 ID
全部换成空配置态，把一份「粘上就能跑」的文件降级成「还得逐个选库表」的骨架。
**真实资源 ID 只能从画布取，丢了就得用户一个个重新选。**

### 正确动作：四步

1. **先体检，再动手**：拿现成文件跑 `validate_workflow.py`。
   如果它是 `error 0 / warning 0 / 未配置项 0`，说明**结构没问题** ——
   那用户要的「优化」就不在规则覆盖的范围内（见第 3 步），不要在结构上乱改。
2. **外科手术式打补丁**：只改有问题的字段，保留其余全部字节（包括 `icon` URL、
   `_temp.externalData` 里缓存的子工作流元数据、`bounds`、`rawMeta` 编码）。
   用一个 patch 脚本 `load → 定点改 → dump`，**不要走 `build_workflow.py`**。
3. **去找「规则查不出、但会影响效果」的问题**。这一步才是优化的价值所在，实测清单：
   | 类型 | 例子（WF-8 实例） |
   |---|---|
   | **参数退化**：入参绑得比设计弱 | 知识库检索的 `Query` 只绑了 `v_guide_type`（"选题"两个字），设计要的是「类型 + 作品 + 指导 + 项目 + 学生问题」，`in_question` 白传了 |
   | **同一字段两处写法** | `school_type` 在代码节点里读过一次，又被两处用数组点路径 `q_profile.school_type` 直接引 —— 统一到代码节点的输出口 |
   | **判定过松导致空值穿透** | `registered = len(q_profile) > 0`：查到一行空记录也算「已建档」，于是把一整串空字段丢给大模型硬编指导 |
   | **无人引用的冗余输出** | 占位节点多输出一个空 `llm_guide`，实际没人引 |
   | **命名与设计文档对不上** | 聚合组叫 `Group1`，而文档的变量总表写的是 `v_message`（组名即输出名，改名零成本） |
   | **死代码 / 缺类型兜底** | `normalize_guide` 的 alias 里有条永不命中的项；`p.get('q_profile')` 没做 `isinstance(list)` |
4. **用 diff 自证**：跑一份「资源 ID 集合对比 + 逐路径差异清单」，
   把「ID 一个没变」和「改了什么」都摆出来。这比说「我优化了」可信得多。
   ```python
   IDS = ("databaseInfoID", "fieldID", "workflowId", "workflow_id", "plugin_id", "spaceId", "space_id")
   # 递归收集两边的 ID 集合 → 必须完全相等；再 walk 一遍列出所有差异路径
   ```

### 一句话判据

> **有真实 ID 的文件 → 打补丁；只有需求/文档 → 从零生成。**
> 判断方法：跑一次校验器，看「未配置项」是 0 还是有值 —— 0 就说明 ID 是齐的。

### 顺带：改名会破坏下游引用，改完必须复验

`Group1 → v_message` 这类改名，下游 `结束` 节点的 ref 也要同步改。
改完**必须重跑校验器**（`E5` 专抓 ref 指向不存在的变量名），再跑一次自定义的 ref 断链扫描。
本例改了 3 处引用（聚合组名、聚合输出名、结束节点 ref），校验器 `error 0` 才交付。

## 12.14 ★★★ 最贵的一类 bug：**文档是对的、生成器是错的、没有规则查**

### 现场

用户贴了一张画布截图：查询数据节点的「**查询字段**」整列显示 `undefined`，
「**查询条件**」左侧显示一串**裸数字** `1831982593025`。

而技能自己的文档 **08 + 09 早就写对了**：

- `04` §12 的骨架里 `left` 写的是 `"content":"review_status"` → **字段名**
- `09` §「认表方法」明写「`conditionList[].left` 是字段**名**，不是 ID」

**可生成器 `coze_node_lib._db_condition()` 把两处都写反了**：
`left` 调了 `_as_field_id()` 转成 ID；`fieldList[].fieldID` 输出成字符串。
而**校验器没有任何规则覆盖这两处** —— 于是错误静默地复制到了每一个生成的文件里
（WF-8 的 4 个查询节点 ×2 处问题 = 8 处，WF-9 同样，以及此后所有新文件）。

### 为什么能藏这么久

| 环节 | 表现 |
|---|---|
| 粘贴 | ✅ 正常 —— 平台不校验这些字段的形态 |
| 校验器 | ✅ `error 0` —— 当时没有对应规则 |
| 运行 | ❓ 大多「看起来能跑」（条件可能被当成字符串比较，悄悄漏掉匹配） |
| **画布面板** | ❌ **一眼看得见**，但只有打开那个节点才看得到 |

**所以：唯一可靠的发现途径是「打开画布上的节点面板看一眼」，或者静态检查。**

### 修法（三件事一起做，缺一不可）

1. **改生成器**：`left` 原样输出字段名（不转换）；`fieldList`/`orderByList` 用 `_as_field_id_num()`
   输出**数字**；`fieldInfo` 保持**字符串**（它和 fieldList 故意相反）。
2. **加校验规则 `E19`** 把它钉死，否则下次还会重犯：
   - `fieldList[].fieldID` 是字符串 → **error**（画布会整列 undefined）
   - `conditionList[].left` 是纯数字 → **error**（画布显示裸数字）
   - `fieldInfo[][0]` 是数字 → **warning**（与真实样本相反）
3. **写进文档并标证据等级**：三种写法对照表进 `04`，同表进 `09`，并注明证据是
   4 份真实画布采集样本（`wf_onboarding` / `wf_flow_guide` / `wf_review_start` / `wf_stage_advance`）。

### 可复用的三条规矩

1. **「文档写了」不等于「代码做了」。** 生成器和参考文档是两套东西，必须交叉验证。
   发现矛盾时**以真实样本为准**，然后**两边都改**。
2. **凡是「粘贴不报错、运行也不明显报错」的字段形态，都必须有校验规则。**
   没有规则 = 会在所有产出里静默复制。判断要不要加规则，问一句：
   *「写错了会有人发现吗？」* 靠人眼才能发现 → 立刻加规则。
3. **加完规则要拿历史文件回归。** 本例用 `E19` 回归 WF-8 立刻报出 8 处 error ——
   回归成功本身就是「这条规则有价值」的证明。同时要确认**不误报**技能自带的样例
   （`E17`/`E18` 都因为对「单节点采集片段」误报而加了前置条件）。

> 对比一下本文件里其他几条规则的价值来源：
> `E16`（缺 bounds → 粘贴毫无反应）、`E17`（节点不可达 → 静默不执行）、
> `E18`（意图分支悬空 → 画布可见）、`E19`（字段写法反 → 画布可见且静默影响匹配）。
> **四条里有三条都是「用户看不出来、我事先也没想到」** —— 这正是校验器存在的意义。

## 12.15 ★★ 拿到一批真实样本时，用「批量事实抽取」代替逐份阅读

用户一次丢来 3~5 份真实画布 JSON（或整份 `wf_*.md` 采集文档）时，
**不要逐份读**（读不完，且看不出规律）。写一个脚本，把「每种写法出现过几次」做成计数器：

```python
from collections import Counter
fid_types, left_forms, ops, group_names, rawmeta_types = Counter(), Counter(), Counter(), Counter(), Counter()
for doc in samples:
    for node in doc["json"]["nodes"]:
        sp = node["data"]["inputs"].get("selectParam")
        if isinstance(sp, dict):
            for f in sp["fieldList"]:                       fid_types[type(f["fieldID"]).__name__] += 1
            for row in sp["condition"]["conditionList"]:
                for c in row:
                    v = c["input"]["value"]
                    if c["name"] == "left":      left_forms[
                        "字段名" if not str(v.get("content", "")).isdigit() else "数字"] += 1
                    if c["name"] == "operation": ops[v["content"]] += 1
                    if c["name"] == "right":     rawmeta_types[(v.get("type"), (v.get("rawMeta") or {}).get("type"))] += 1
        if str(node.get("type")) == "32":
            for g in node["data"]["inputs"].get("mergeGroups") or []: group_names[g["name"]] += 1
print(dict(fid_types), dict(ops), dict(group_names), dict(rawmeta_types))
```

**2026-09-21 实测输出（4 份样本）**：

| 计数器 | 输出 | 读法 |
|---|---|---|
| `fieldList.fieldID` 类型 | `{'int': 65, 'insert:str': 33, 'update:str': 11}` | 查询=**数字**、写入=**字符串**，两边都实测 |
| 条件 `left` | `{'字段名': 15}` | **15/15 都是字段名**，没有例外 |
| `operation` | `{'EQUAL': 13, 'LIKE': 2}` | **两个都合法** —— 拿到 LIKE 的实测值了 |
| `right` 的 rawMeta | `{('ref',2):4, ('ref',1):9}` | type 2=整数、type 1=字符串 |
| 变量聚合组名 | `{'Group1':1, 'out_tip':1, 'out_milestone':1, 'v_message':1}` | **自定义组名是原生用法**，不是异想天开 |
| 点路径引用 | `{'outputList.字段': 5}` | **对列表输出用点路径**也是原生用法 |

### 三条读法

1. **计数器的取值有多个 = 这些取值都合法**（`operation` 有 EQUAL 和 LIKE → 都能用；
   组名有 4 种 → 随便起名）。这比猜「平台支不支持 X」快得多。
2. **只有一种取值的东西 = 硬约束**（`left` 15/15 都是字段名 → 那一格写别的就是错）。
3. **计数器里出现的类型/形态，拿去和生成器输出对表。** 不一致的就是生成器 bug ——
   本次就是靠 `{'int': 65, ...}` 一眼看出「生成器把 fieldList 写成了字符串」。

### 必做：拿真实样本跑一遍校验器当「不误报回归」

规则写完要证明它**不会在平台原生文件上乱报**。本次：

```
wf_flow_guide    15 节点 / 15 连线 → error 0，warning 0，未配置项 0
wf_stage_advance 11 节点 / 11 连线 → error 0，warning 0，未配置项 0
wf_onboarding    21 节点 / 23 连线 → error 0，warning 0，未配置项 0
```

**三份真实样本全部 0 error 0 warning** —— 这才是 `E16~E19` 可以放心用的依据。
反过来，如果真实样本报 error，**先怀疑规则的判据错了**，而不是去改样本。

### 顺带：形状比对是最终验收

修完之后，**把「生成的文件」和「同类真实样本」逐项对齐打勾**，比说「我修好了」可信得多：

```
项目                        | 真实样本 wf_flow_guide | 修正后 WF-8
fieldList[0] 类型            | int                   | int          ✅
条件 left                    | user_id               | user_id      ✅
条件 operation               | EQUAL                 | EQUAL        ✅
条件 right input.type        | integer               | integer      ✅
right ref rawMeta            | 2                     | 2            ✅
schema.user_id 类型          | integer               | integer      ✅
```


## 12.16 ★ 修复流水线必须是「从原始文件到最终产物」的完整闭包

**这是本项目最隐蔽的一次翻车：交付物看着完全正常，实质内容却被静默回退。**

### 症状

产物文件名还叫 `_优化版.json`，跑校验器仍然 `error 0 · warning 0 · 未配置项 0`，
`diff` 一比也「只有预期的差异」—— 但用户贴进画布后发现，先前承诺的 6 项语义优化
（检索语句、取值口统一、组名、冗余输出、判定收紧、代码健壮性）**全都不在**。

### 根因

修复被拆成了**两个各自独立、都能跑通**的脚本：

| 脚本 | 做什么 | 从哪读 | 写到哪 |
|---|---|---|---|
| `patch_wf8.py` | O1~O7 语义优化 | 原始文件 | `_优化版.json` |
| `pipeline_wf8_wf9.py` | E19 字段写法 + 类型/操作符 | **原始文件** | `_优化版.json` |

第二个脚本**只包含后两步**，却从原始文件出发、直接覆盖了第一个脚本的产物。
于是「两步」覆盖了「三步」，而且**没有任何一步会报错**。

### 为什么难发现（三个伪装同时生效）

1. **文件名不变** —— `_优化版.json` 仍在，看着就像同一条产线出的。
2. **校验器只查结构合法性，不查「优化项在不在」** —— 少了几项优化，结构完全合法。
3. **diff 的方向错了** —— 一直在比「原版 vs 优化版」，而这次需要比的是
   「上一版产物 vs 这一版产物」（**跨版本对比**），否则看不见「某一步整个消失」。

### 做法（四条，缺一不可）

**① 一条流水线 = 从原始文件到最终产物的完整步骤序列**，中间用临时文件串，只在最后落最终产物。

```python
# 顺序有依赖，不能换：语义优化 → 字段写法 → 类型/操作符
subprocess.run([PY, "patch_wf8.py"])     # 第 1 步：O1~O7（自行写 _优化版.json）
F1.fix(WF8_OUT, TMP)                     # 第 2 步：E19 → 临时文件
F2.fix(TMP, WF8_OUT)                     # 第 3 步：类型 → 最终产物
os.remove(TMP)
```

**② 交付前跑「自检清单」：每条承诺的优化项 = 一条机器断言。**

```python
def ck(tag, desc, ok, detail=""):
    checks.append((tag, desc, bool(ok), detail))

ck("O1", "知识库 Query 绑 v_kb_query",
   by_name("100010", "Query")...get("name") == "v_kb_query" and "v_kb_query" in outs("100003"))
ck("O5", "建档判定收紧",
   "registered = bool(school or major)" in code3)
...
print("  ---- %d / %d 项通过" % (ok, total))
```

**③ 自检不过就 `exit 1`，产物按「不可交付」处理**（本次实跑输出 `10/11` → 先修断言再交付）。

**④ 断言失败时先怀疑断言本身。** 本次 `T2` 报错是自检脚本把
`input.type` 读成了 `value.type`（类型标在 `input` 层，`value` 里只有 `{type:"ref",...}`）——
文件其实是对的。**自检脚本也是代码，也会错**，所以报错时要打开产物人工确认一次再改。

### 通用判据

> **交付说明里承诺了什么，就要有对应的机器断言。**
> 只写在文档/回复里的优化项，等于没做 —— 下一轮重跑就可能静默消失。

### 顺带：跨版本对比要留档

`diff` 的作用是「证明改动落在预期范围内」。但当流水线可能**整体丢步骤**时，
必须能 diff「上一个交付版本」而不是只 diff 原始文件。
**建议每版产物另存一份带版本号的快照**（如 `_优化版_v2.json`），否则没有对比基准。


## 12.17 跨分支 / 跨循环的「引用完整性」——结束节点绝不能引用只在某条路径上执行的节点

WF-10（导师看板）按文档画出来后暴露了两个纯净的结构缺陷。**这两个坑不报错、能粘贴，
只在运行时表现为「字段为空」或「统计恒为 0」**，属于必须靠设计阶段拦下来的类型。

### 坑 1：分支下游的节点，被不经过它的另一条路径引用了

文档结构：`前置校验 → 选择器`，`true → 循环 → 汇总统计 → …`，`false → 直接到聚合`。
而**结束节点引用了 `汇总统计.out_count` / `out_overdue`** —— 它在 false 路径上**根本没执行**。

```
结构：  校验 ──true──→ 循环 → 汇总统计 ──┐
          └────false───────────────────┴→ 聚合 → 结束
                                               ↑
                       结束引用 汇总统计.out_count ← false 路径上没有这个节点
```

**判据（一句话）**：从「开始」出发，若某节点 N 只在分支 B 上执行，
则**任何在 B 之外也会执行的节点**（尤其是结束节点）都不能引用 N 的输出。

**修法（不加节点）**：让**分支之前**的节点顺带产出「兜底常量」，交给变量聚合分组取值。

```python
# 在分支前的代码节点里（它两条路径都执行）
ret = {"v_ok": "Y" if count else "N", "v_count": count, "v_zero": 0, "tip_text": tip}
```
```jsonc
// 变量聚合拆成 3 组：真分支的产出排第一，兜底常量排第二
"merge_groups": [
  {"name": "v_message", "variables": ["汇总统计.out_summary", "前置校验.tip_text"]},
  {"name": "v_count",   "variables": ["汇总统计.out_count",   "前置校验.v_count"]},
  {"name": "v_overdue", "variables": ["汇总统计.out_overdue", "前置校验.v_zero"]}
]
```
结束节点改为**只引用聚合输出**（聚合在任何路径上都会执行）。
这样节点数不增、结构极简，且**每个字段在每条路径上都有定义**。

> 组名即输出名，所以 `v_count` / `v_overdue` 直接就是结束节点的入参名。
> 附带好处：`v_count`/`v_overdue` 是 Integer 组，与 `v_message`（String）分开 —— 顺带满足「组内类型必须一致」。

### 坑 2：循环的输出默认取「循环体末节点」，而末节点可能是拿不到数据的那个

文档把循环体设计成 `查进度 → 里程碑 → 组装数据 → 写飞书表格`，
而下游要统计的是**每轮的逾期布尔**（来自「组装数据」）。循环体末节点却是那个插件，
它的回执里没有逾期信息 → 统计恒为 0。

**修法**：用 `loop_output` **显式指定**输出来自哪个体内节点，不要依赖「末节点」这个默认。

```jsonc
"loop_output": {"name": "items", "block": "400008", "var": "v_is_overdue",
                "type": "list", "items": "boolean"}
```
```python
# 同时让消费端对「形态」宽容一点：可能是布尔，也可能是 {v_is_overdue: bool}
for it in items:
    if isinstance(it, dict):
        if it.get('v_is_overdue'):
            overdue += 1
    elif it:
        overdue += 1
```

> 记住：**循环节点对外的输出只能来自循环体内某个节点，由 `outputs[].input.value.content.blockID` 指定**。
> 凡是「循环体里既有业务计算、又有副作用节点（写库/发消息/写表格）」的结构，**都必须显式指定**。

### 顺带：别对「节点数」的两个口径感到困惑

`validate_workflow.py` 打印的「节点 N 个」只数**顶层节点**；
循环/批处理体内节点在 `blocks` 里另算。WF-10 显示「10 节点」，加上体内 4 个才是文档说的 14 个。
`E16` 的 bounds 也只由根层节点决定 —— 别用「节点数对不上」去怀疑文件错了。

### 附：文档内部自相矛盾时怎么办

WF-10 文档第 284 行提醒「`student_profile` 表里得有 `school_type` 字段」，
但同一份文档 N02 的查询字段清单里**没有 `school_type`**（而循环体要用 `stu.school_type`）。
**处理原则：以满足「下游真正需要的字段」为准去补上游的查询字段**，并在节点 `description` 里
写清这是对文档的补正 —— 不要留着它在运行时变成空值。
