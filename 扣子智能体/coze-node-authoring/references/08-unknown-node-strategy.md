# 08 · 遇到"编号未知"的节点怎么办（本次实践最重要的方法论）

写代码生成工作流时，**一定会撞上"这个节点的 type 编号我没实测过"**。本技能采集了 8 份真实工作流、45 个节点，也只覆盖了 13 种类型；官方 DSL 里还有 40 多种。

处理方式分三层，**从"最不该做的"到"最该做的"**：

| 做法 | 评价 |
|---|---|
| 按顺序猜编号（"42/43 是数据库，那 44 就是删除"） | ❌ 绝对禁止。实测编号跳号严重（`1,2,3,4,5,6,8,15,21,32,42,43,46`），猜错会导致整份 JSON 粘不上 |
| 查二手文章找编号 | ⚠️ 不可靠。本次核实中，多篇文章的把 DSL 英文名和剪贴板数字混着写 |
| 实测一次，固化到 `node_type_overrides.json` | ✅ 正确做法，30 秒成本 |
| **用"接口等价占位节点"先把整条工作流跑通** | ✅ 工程上最优，编号问题不阻塞主流程 |

## 手法一：实测固化（正式做法）

```bash
# 1) 画布上添加一个「工作流」节点（随便选一个子工作流）
# 2) 单击该节点 → Ctrl+C
# 3) 粘到记事本（或任意文本框）→ 找 "type":"N"
# 4) 写进覆盖表
```

`scripts/node_type_overrides.json`：

```json
{ "subflow": "13", "delete_database": "44" }
```

之后 `build_workflow.py` 里就能直接写 `"type": "subflow"`。**这份文件是你自己的实测成果，本技能只提供空模板，不预填任何猜测值。**

## 手法二：接口等价占位（推荐，遇到就先用这个）

**核心思路：先把"接口"定死，实现后换。**

一个节点对上下游其实只有三件事有意义：**位置（连线）、输入变量名、输出变量名**。类型编号只影响"内部怎么算"。

所以在撞上未知类型时，**用一个 `代码节点` 顶上去**，把输出变量名和类型写得和真节点一模一样：

```json
{
  "id": "100005",
  "type": "代码",
  "title": "里程碑查询（占位·待换工作流节点）",
  "description": "原节点为「工作流节点：调用 wf_milestone_get」。该类型剪贴板编号未实测，故用接口等价的代码节点占位。",
  "inputs": {
    "v_school": "100003.v_school",
    "v_college": "100003.v_college",
    "v_major": "100003.v_major",
    "school_type": "100002.q_profile.school_type",
    "in_now_ts": "100001.in_now_ts"
  },
  "code": "async def main(v_school: str, v_college: str, v_major: str, school_type: str, in_now_ts: int) -> dict:\n    return {\n        \"ms_out_list\": [],\n        \"ms_out_source\": \"占位\",\n        \"ms_out_found\": False,\n        \"ms_out_current_task\": \"\",\n        \"ms_out_current_range\": \"\",\n        \"ms_out_next_task\": \"\",\n        \"ms_out_next_range\": \"\",\n        \"ms_out_days_left\": 0,\n        \"ms_out_is_overdue\": False,\n    }\n",
  "outputs": [
    {"name": "ms_out_list", "type": "list", "items": "object", "schema": {"type": "object", "schema": []}},
    {"name": "ms_out_source", "type": "string"},
    {"name": "ms_out_found", "type": "boolean"},
    {"name": "ms_out_current_task", "type": "string"},
    {"name": "ms_out_current_range", "type": "string"},
    {"name": "ms_out_next_task", "type": "string"},
    {"name": "ms_out_next_range", "type": "string"},
    {"name": "ms_out_days_left", "type": "integer"},
    {"name": "ms_out_is_overdue", "type": "boolean"}
  ]
}
```

**这样做换来四个好处：**

1. **整条工作流可以立刻粘贴、立刻试运行** —— 不会因为一个节点卡住全部验收。
2. **结构风险提前暴露**：连线对不对、变量引用全不全、下游提示词有没有漏变量，都能在占位阶段验证完。
3. **换实现时只改一个节点**：真节点的输出变量名完全一致，下游的 `ref` 一个都不用动。
4. **顺带把"接口契约"写成了可执行的文档** —— 占位代码里的 9 个键就是这份契约，比写在 Markdown 表格里更难被忽略。

**换法**：画布上把占位代码节点删掉 → 添加真正的「工作流」节点 → 选 `wf_milestone_get` → 按上面 `inputs` 表填入参映射 → 输出名照抄 → 把上下游连线接回去。

⚠️ 代价：必须**在交付说明里明确写出"这是占位"**，并给出替换步骤。**绝不能默默用占位节点冒充真节点**——用户会以为已经做完了。

## 手法三：raw_data 逃生舱（已知类型、但结构没吃透时）

对"已知编号但字段结构没把握"的节点，先手工在画布上**把这一类节点配好一个**，复制出来，把它的 `data` 整块贴进规格：

```json
{
  "id": "100020",
  "type": "13",
  "title": "里程碑查询",
  "raw_data": { "...从画布复制出来的 data 整块..." },
  "inputs": { "in_school": "100003.v_school" }
}
```

`raw_data` 会整块接管 `data`，库只做两件事：**用 `inputs` 里的简写替换同名参数的值**、**改写 `nodeMeta.title`**。这样"复制一次、之后批量复用"成为可能。

## 三条纪律

1. **交付物里必须能一眼看出哪些是占位**。标题加"（占位·待换…）"、`description` 写明原因、`FILL_ME_*` 前缀标记待填 ID。
2. **占位节点的输出变量名 = 真节点的输出变量名**，一个字符都不能差，否则"换实现只改一个节点"这个最大好处就没了。
3. **不要在技能/脚本里预填任何未实测的编号**。宁可报错 + 打印实测步骤，也不给出一个"看起来对"的数字。


## 手法三（首选）：**代码节点占位** —— 类型不确定但要先让画布立起来

当用户只给了**文字描述或截图**，某个节点的类型判断不了（分不清是插件、子工作流还是代码），
而你又想先产出一份**能粘上画布**的骨架时：

> **用一个「代码节点」占位，不要猜成插件。**

### 为什么是代码节点

| 候选 | 需要资源 ID？ | 粘贴会不会被拦 |
|---|---|---|
| 插件 `4` | **要** `pluginID` + `apiID` | ❌ 查不到就**阻断导入**（弹红条） |
| 工作流 `9` | **要** `workflowId` + `version` | ❌ 同上 |
| 知识库类 | **要** `datasetList` | ❌ 同上 |
| **代码 `5`** | **一个都不要** | ✅ **能粘** |

**代码节点是唯一「零资源依赖」的通用容器。** 所以拿它当占位，可以让**整条流程的骨架先立起来**：
用户在画布上能看到正确的节点数和连线，再逐个把占位换成真节点。

### 占位代码要自带说明

```python
# ======================================================================
# ⚠️ 占位节点：这里原本是「查询历史文档」。
#    真身大概率是 插件 / 子工作流 —— 它们需要真实的 pluginID / apiID，
#    缺失时平台在粘贴阶段就会拒绝导入，所以这里先用代码节点占位。
#    替换方法：把那个节点的真实剪贴板 JSON 发我，我换成正确类型。
# ======================================================================
async def main(args: Args) -> Output:
    p = args.params
    ret: Output = { ... }
    return ret
```

**注释写在代码里**，这样用户在画布上点开节点就能看到「这里该放什么」，不用回头翻文档。

### ⚠️ 两个必须注意的实现细节（都踩过）

1. **占位代码的正文必须落在字典字面量里**。如果占位逻辑需要 `import` 或中间变量
   （例如算 hash），要放在 `ret: Output = {` **之前**，不能塞进 `{ }` 里 —— 否则 AST 校验会报
   `代码语法错误：invalid syntax`。（`build_workflow.py` 的 `_wrap()` 已支持 `pre` 参数。）
2. **不要在占位代码里用 `hash()`** —— 它跨进程不确定。用确定性算法（如 `sum(ord(c) for c in s)`）。

### 顺带一条：交付时必须给「可信度说明书」

从文字描述/截图还原时，**只给 JSON 是不负责任的**。要同时给一张表，逐节点标：
- 类型判定依据 + 置信度（✅高 / 🟢中高 / 🟡中 / ❌待定）
- 哪些字段是**占位**（提示词、代码、资源 ID）
- 具体**冲突点**（描述与平台实测对不上的地方）

用户才能判断「这份东西能用到什么程度」。

## 同样的逻辑适用于"平台侧生成的 ID"

以下东西**无法凭空生成，只能从画布取**：

| 项 | 出现位置 |
|---|---|
| `databaseInfoID` | 数据库查询/新增/更新节点的 `inputs.databaseInfoList[0]` |
| `fieldID` | 数据库节点的 `fieldList[].fieldID`、`conditionList[].left`、`fieldInfo[][0]` |
| `datasetList`（知识库 ID） | 知识库检索节点的 `datasetParam` |
| `apiID` / `pluginID` | 插件节点的 `apiParam` |
| `workflowId` | 工作流（子工作流）节点的 `inputs` |
| `modelType` | 大模型节点的 `llmParam`（换模型时必须实测） |

### ⚠️ 但这些**不能用 `FILL_ME_*` 占位**（实测教训）

2026-09-19 真实翻车：生成的工作流里知识库 ID 用 `FILL_ME_flow_kb_id` 占位，粘贴时平台**直接弹红条阻断导入**：

```
❌ 知识库 FILL_ME_flow_kb_id,FILL_ME_academic_kb_id不存在
```

**分两类，处理方式完全不同：**

| 类型 | 例子 | 占位后果 | 正确做法 |
|---|---|---|---|
| **资源类**（平台在粘贴/保存时强校验存在性） | `datasetList`、`databaseInfoID`、`apiID`/`pluginID`、`workflowId` | ❌ **粘贴直接失败** | **必须填真值**，或整个节点先不画 |
| **普通字段**（平台不校验） | 代码、提示词、变量名、`fieldID` | ✅ 能导入，运行时才出问题 | 可用 `FILL_ME_*` 占位 |

**所以：资源类 ID 一律去"挖"，不要填占位。** 做法见 `references/09-harvest-real-ids.md` —— 同一空间里**你已发布的工作流里就有这些 ID**，用 `scripts/harvest_ids.py` 批量挖出来复用，比在画布上一个个点快得多。

`validate_workflow.py` 的 **E15** 就查这个：资源位出现 `FILL_ME` 判 **error**；普通位的 `FILL_ME` 判 **warning**。
