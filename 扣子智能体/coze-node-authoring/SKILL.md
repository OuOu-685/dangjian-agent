# coze-node-authoring

把 Coze 工作流当成**可生成的数据结构**来操作。核心结论只有一句：

> **Coze 画布的复制/粘贴载体是 `coze-workflow-clipboard-data` JSON。能写出这份 JSON，就能用代码生成、修改、批量生产节点——不需要点画布。**

## 三条必须先记住的事实（决定整个做法）

**事实 0（最贵的一条，已单变量实证）：信封层必须有顶层 `bounds`，缺了会「按 Ctrl+V 毫无反应」。**
`bounds` 是 `type`/`source`/`json` 的**兄弟字段**（**不是** `json.bounds`），值 = **所有根节点 `_temp.bounds` 的并集**（13/13 实测精确吻合，浮点误差 < 1e-6）。
漏写它的症状是**完全静默**——不报错、不提示、不出现任何节点，极易被误判成「平台禁止外部 JSON 粘贴」。
`validate_workflow.py` 的 `E16` 专守这条。详见 `references/01-clipboard-envelope.md` §1.1。

**事实 1：存在两套互不兼容的格式，网上大量文章把它们混为一谈。**

| | 剪贴板格式（本技能主角） | 官方 DSL 导出格式 |
|---|---|---|
| 顶层标识 | `"type":"coze-workflow-clipboard-data"` | `schema_version: "1.0.0"` |
| `type` 字段 | **数字字符串** `"1" "3" "21"` | **英文名** `start` `llm` `loop` |
| 节点载荷 | `data.nodeMeta` + `data.inputs` + `data.outputs` | `parameters.node_inputs` / `node_outputs` |
| 值引用 | `{"type":"ref","content":{"blockID":"…","name":"…"}}` | `{ref_node: '100001', path: 'input'}` |
| 连线 | `sourceNodeID` / `targetNodeID` | `source_node` / `target_node` |
| 用途 | **Ctrl+V 直接粘进画布**（免费可用） | 会员「导入」按钮 |

**写给人看、给 AI 读**时用 DSL 的英文名（有官方字段表）；**实际交付给用户去粘贴**时产出剪贴板格式。两者不要混着拼。

**事实 2：剪贴板格式没有官方文档，它的字段是从真实文件反推的。** 所以本技能里每条字段都标了证据等级：`[实测]` = 在 ≥1 份真实工作流样本中出现过；`[官方]` = 官方文档明文；`[未证实]` = 网上有说法但样本中未出现——**不要拿 `[未证实]` 的字段去猜**。

**事实 3：节点 `type` 数字不是顺序编号，不要按"第 N 个节点就是 N"去推。** 已实测：`1/2/3/4/5/6/8/9/12/15/18/21/22/28/32/42/43/44/45/46/58/59`（跳号极其严重）。具体对照见 `references/02-node-type-map.md`，其中**明确列出未证实的编号**，遇到就实地验证而不是猜。

**事实 4：撞上"编号未知"的节点时，不要猜，用两步走。** 先看 `references/08-unknown-node-strategy.md`：手法一是**在画布上复制一次节点拿到编号**（30 秒）写进 `scripts/node_type_overrides.json`；手法二是**用「接口等价的占位节点」先把整条工作流跑通**，编号问题不阻塞主流程。这条在实战里救了整条流水线。

**事实 5（用户明确定下的规矩）：数据不足时产出「空配置态」节点，绝不自己编内容。**

参数缺失时有两种诱人但**都错**的做法：① 自己编一段提示词 / 意图名 / SQL 填上；② 填 `FILL_ME_xxx` 占位 ID。
**正解是产出平台原生的「空配置态」** —— 它**能正常粘贴**，粘上去后由用户在画布上补配置：

| 类型 | 空配置态（实测的平台原生写法） |
|---|---|
| 查询数据 `43` | `databaseInfoList: []` + `selectParam: {"condition": {"logic": "AND"}}`（**不写** `fieldList`/`orderByList`/`limit`）|
| 更新数据 `42` | `databaseInfoList: []` + `updateParam: {"condition": {"logic": "AND"}}` |
| 新增数据 `46` | `databaseInfoList: []`，**完全没有 `insertParam` 键** |
| 删除数据 `44` | `databaseInfoList: []` + `deleteParam: {"condition": {"logic": "AND"}}` |
| SQL自定义 `12` | `databaseInfoList: []` + `inputParameters: []`（SQL 文本字段名未证实，**不要编**）|
| 知识库检索 `6` | `datasetList: []`，且 `datasetParam` 是 **7 项**（选了知识库才是 9 项）|
| 意图识别 `22` | `intents: [{"name": ""}]`、`inputParameters: []`、`prompt: "{{query}}"` |
| 大模型 `3` | `prompt: ""`、`systemPrompt: ""`（其余字段走平台默认值）|
| 问答 `18` | `options: [{"name":""},{"name":""}]`、`question: ""` |

**为什么空态能粘**：它**不引用任何资源**，就不触发资源存在性校验。
`FILL_ME_xxx` 会触发 → 弹红条阻断导入；**空数组不会** → 正常进画布。
⚠️ 特别注意 `[{"databaseInfoID": ""}]` 这种「有条目但 ID 为空」是**畸形值**（会被拿去查资源然后失败），
未配置必须写**空数组 `[]`**。

**唯一的例外**：用户或文档**明确给了**内容（提示词原文、意图名清单、模型名、参数名）→ 照抄，那不算"编"。

交付时用 `validate_workflow.py` 的「未配置项」清单（`ℹ️` 段）告诉用户**哪些节点需要他自己补**，
而不是替他把业务内容填上。详见 `references/11-empty-state.md`。

## 三种典型任务，走三条路

### 任务 A：从零生成一整条工作流（最常用）

用 `scripts/build_workflow.py` + 一份**紧凑规格 JSON**，自动产出可直接粘贴的剪贴板 JSON。

```bash
python scripts/build_workflow.py spec.json -o out.json
```

规格只写"业务语义"，脏活（值引用编码、rawMeta、位置排布、`_temp` 尺寸、异常处理默认值）由脚本补。规格长这样：

```json
{
  "name": "校园新闻审核",
  "space_id": "7493357645614039092",
  "nodes": [
    {"id": "100001", "type": "start", "title": "开始",
     "outputs": [{"name": "draft_text", "type": "string", "required": true}]},
    {"id": "171354", "type": "code", "title": "文本分段",
     "inputs": {"draft_text": "100001.draft_text"},
     "code": "async def main(draft_text: str) -> dict:\n    ps = [s.strip() for s in draft_text.splitlines() if s.strip()]\n    return {\"paragraphs\": ps, \"total\": len(ps)}",
     "outputs": [{"name": "paragraphs", "type": "array", "items": "string"},
                 {"name": "total", "type": "integer"}]},
    {"id": "900001", "type": "end", "title": "结束",
     "inputs": {"paragraphs": "171354.paragraphs"}}
  ],
  "edges": [["100001", "171354"], ["171354", "900001"]]
}
```

`"100001.draft_text"` 这种字符串就是引用简写，脚本会展开成完整 ref 结构。规格字段全表见 `references/04-node-schemas.md`。

### 任务 B：生成 / 改造单个节点

不要整条重写，只造那一个节点对象，然后贴进已有 `nodes` 数组、补上 `edges`。
- 每种节点的**最小可运行骨架**（含真实字段值）→ `references/04-node-schemas.md`
- 值的写法（引用 / 固定值 / 数组 / 对象）→ `references/03-value-and-types.md`
- 连线和分支端口名（`true` / `false` / `loop-output` …）→ `references/05-edges-and-ports.md`

### 任务 C：解析 / 校验 / 迁移一份已有工作流

```bash
python scripts/validate_workflow.py flow.json          # 体检
python scripts/validate_workflow.py flow.json --json   # 机器可读输出
```

校验覆盖 16 类问题，其中 6 类是人工肉眼查不出来的：代码节点**每个 `return` 分支的键是否都齐**、`ref` 指向的 `blockID` 与变量名是否真实存在、选择器是否缺 `else` 分支、循环节点是否漏了内嵌 `blocks`、**节点是否从「开始」可达**（不可达 = 静默不执行）、**数据库字段的三种写法是否写反**（画布上表现为 undefined / 裸数字）。清单见脚本头部注释与 `references/05-edges-and-ports.md`。

## 写代码节点（用户最常卡住的地方）

**结论：Python 3.11.3 沙箱，只能 `params['名']` 或直接形参，只能有一个函数，必须 `return` 一个对象，60 秒超时，只内置 `requests_async` 和 `numpy`。**

官方于 2025-09-16 升级过代码节点服务，于是样本里出现了**三种签名**，全部可用：

```python
# 样式① 旧版（官方文档主推）
async def main(args: Args) -> Output:
    params = args.params
    return {"out": params["in1"]}

# 样式② 新版直接形参 —— 形参名必须与 inputParameters 的 name 逐一对应
def main(task_book: dict) -> dict:
    return {"is_valid": True}

# 样式③ 新版 + 异步
async def main(task_book: str) -> dict:
    import json
    return {"is_valid": bool(json.loads(task_book).get("modules"))}
```

⚠️ 新手最容易踩的三条 → 详见 `references/06-code-node-python.md`：
1. `Args` **不是 dict**，`args.get(...)` 会报错；要 `dict(args).get(...)` 或 `args.params[...]`。
2. 有的写法要经过平台自动包裹的 `params` 层（`args.params['x']`），有的不用——**看样本里用的是哪种签名，跟着用同一种**。
3. 代码节点**不支持多函数**，也不要写 `print`/`time.sleep`。

## 别被网上文章带偏（已知错误说法）

写这个技能时逐条核实过。以下说法**是错的**，遇到要纠正而不是照抄：

| 错误说法 | 实际 |
|---|---|
| 代码节点用 Python 3.9，靠 `get_input()` / `set_output()` 读写 | Python **3.11.3**，用 `params['x']`；`get_input/set_output` 不存在 |
| 代码节点默认超时 8 秒、要手动开 HTTP 插件才能联网 | 超时 **60s**；`requests_async` 内置，无需开插件 |
| "Coze 没有真正的循环节点，只能线性流程" | 有循环节点（`type:"21"`），且支持**嵌套子节点**（`blocks` + 内层 `edges`）|
| "剪贴板 JSON 就是官方导出格式" | 两套不同格式，见上文事实 1 |
| 用"节点编号 1~10 顺序表"解释 `type` 数字 | 那是**另一套语境的列表**（讲的是组件种类，不是 `type` 字段）。实测编号是 `1/2/3/4/5/6/8/15/21/32/42/43/46` |
| "Chat2Workflow（zjunlp）能生成可直接 Ctrl+V 的 Coze 节点 JSON" | 它是浙大论文项目（arXiv 2604.19667），**主平台是 Dify**，Coze 只是转换目标。中间产物是自定义 `<workflow>` 包着的 `nodes_info + edges`，经 `converter.py --type coze` 产出 **`schema_version:"1.0.0"` 的 DSL YAML，再打成 `Workflow-{name}.zip`**，走平台「导入」按钮（会员）——**不是剪贴板格式，粘不了**。要"描述→可 Ctrl+V"这条链，本技能才是直连的那条。**已读其源码确认（2026-09，interactive 版）**：其 `node_docs/coze.md` 实为 **Dify 风格简化 schema**（类型名 `if-else`/`question-classifier`/`iteration`/`template-transform` 全是 Dify 体系），Coze 转换仅覆盖 ~18 种节点，**无数据库、无知识库、无子工作流、无意图识别**；`autofix.py` 只做语法层修复（json_repair/括号/拓扑），不校验平台粘贴可行性。可借鉴三点：多轮增量修改规则表（"只输出X"=替换/"另外加"=追加/分支范围修改）、JSON 转义一节（`code` 字段一层转义原则）、SAFETY_AUDIT.md 的可 grep 复现安全声明 |
| 结束节点可以多个 | **每条工作流只有 1 个开始 + 1 个结束**（官方原文），输出定义挂在结束节点上 |

完整的"已证实 / 未证实 / 已证伪"三分类见 `references/07-verified-vs-unverified.md`。**凡本技能未列为 `[实测]/[官方]` 的字段，一律先小样验证再批量用。**

### 🔴 「平台不支持 X」这句话，必须有证据（2026-09-25 血泪）

**这是本技能最贵的一次错误。** 早期在 SKILL.md / 说明书里写了
「平台上根本没有 `包含于`，只有 等于/属于/模糊匹配/为空」「没有 IN」——
**这是错的**。官方文档明文列了 8 个运算符，**`IN` 原生支持**。
后果：下游方案把 `fingerprint IN [...]` 无谓地退化成逐条查（多写代码、多花上下文、还可能更慢）。

**根因**：把「我在画布上见过 4 组」当成了「平台只有 4 个」——
**把「观察到的样例」当成了「能力的全集」**。这是归纳法的经典陷阱：
样本里没出现 ≠ 不存在。

**硬规则（写进任何交付物之前自问）**：

| 我要写的论断 | 必须有的证据 |
|---|---|
| 「平台**支持** X」 | 官方文档明文，**或**实测样本出现过 |
| 「平台**不支持** X」 | **官方文档明文说没有**，**或**穷举验证过 —— 否则只能写「我没验证过」 |
| 数字类（上限/默认值/容量） | 官方文档；**查不到就不写数字**，不要估 |

**去哪里查**：`https://www.coze.cn/open/docs/guides/<节点文档页>`。
例：查询数据节点 = `open/docs/guides/database_select_node`。
**优先 WebFetch 官方页，而不是靠记忆或网上转载文章**（转载文章数字经常不一致）。

> 判据一句话：**「不支持」比「支持」更难证明。别把没试过写成不支持。**

## 🔴 平台能力「负面清单」—— 看起来该有、其实没有

> 这张表和上一节是配套的：上一节讲**怎么证明「不支持」**，这张表是**已经证明过的结果**。
> 写节点描述 / 设计方案**之前**先过一遍，能省掉一整轮「用户配不上 → 回传 → 返工」。

| # | 直觉上「应该有」 | 实测 | 绕行方案 | 证据等级 |
|---|---|---|---|---|
| 1 | 数据库**新增/更新**节点的字段值可以选「系统时间戳」 | ❌ **没有这个选项**，也没有 `{{now()}}` 之类表达式 | 加一个代码节点 `int(time.time())`，库节点引用它的输出。**注意**：若同时要写 `created_at` 和 `updated_at`，让它们引用**同一个**变量，别各取一次（会差 1 秒） | 用户画布实测（2026-09-26）：本技能原描述里写了「`created_at` ← 系统时间戳」，用户照着**根本配不上**，只能自己加一个节点 |
| 2 | 数据库**更新**节点的字段值支持表达式运算 | ❌ 只能填**固定值**或**引用上游输出**，不能写 `{{x + 1}}` | 自增 / 拼接 / 条件取值一律提前放代码节点算好 | 官方文档明文（`database_update_node`） |
| 3 | 知识库检索节点可动态选库、可传多个筛选参数 | ❌ **只能静态选库**；输入参数**固定只有 Query 一个** | 多库场景 = 「条件分支 + N 个静态检索节点 + 变量聚合（type 32）」 | 官方文档明文（`guides_knowledge_node`） |
| 4 | 选择器可以有多个分支（「否则如果」） | ❌ `branches` 数组**恒为 1 项** —— 只有 `true` / `false` 两个口，`false` 是隐式「否则」 | 多路分流 = **串多个二分支选择器** | 穷举验证：本项目所有已粘贴成功的样本，`branches` 长度都是 1；校验器 W18 专门查这条 |
| 5 | 数据库**新增**节点能一次插多行 / 能查重 | ❌ 一次执行只插一行；且**没有 WHERE / 查重能力** | 批量插入 = 套循环逐条；查重 = 在循环**外**先批量查一次已有 key，代码里过滤完再循环插入（循环内逐条查会 N 次往返） | 官方文档 + 实测 |
| 6 | 数据库**查询**节点的条件可以「看情况带上」 | ❌ 条件**写死**，做不到「这个条件为空就跳过」 | 别拆 N 个查询节点。做法：**只查一次全量（limit 200），过滤放到下游代码节点里做**。台账/清单类表数据量小，内存过滤丢数据风险可忽略；要在描述里写明「单次上限 200 条」这个边界 | 实测（2026-09-26，本技能第 4 条延伸） |
| 7 | 代码节点里漏连的输入会抛错 / 给空串 | ❌ 不抛错，就是 **`None`** | 这正是「多分支汇合到同一汇总节点」能成立的原因：未走到的路径拿到 `None`，代码里 `or ''` / `or 0` 兜住。**代价**：每个输入都必须在画布上连线，漏连不会报错、只会让回执退化成兜底话术，排查时极易误判成「数据库没写进去」 | 实测（2026-09-26） |

### 🔴 节点数预算：施工图 10 个 → 实际常常 17 个，这是正常的

**不要为了「逼近施工图节点数」去砍掉必要的节点。** 用户看到节点数对不上，最怕的是
「不知道是不是 AI 乱加的」。正确做法是**把差异列成表一起交付**：

| 施工图写法 | 平台实际 | 因此必须补 |
|---|---|---|
| 查重挂在「新增数据节点」 | 新增节点没有 WHERE（负面清单 #5） | +1 查询 +1 判空代码 +1 重复回执 |
| N 个动作用「多分支选择器」 | 选择器恒为 2 口（#4） | 每多一个动作 +1 个串联分流选择器 |
| 时间戳 = 系统时间戳 | 没有这个选项（#1） | 顺带在已有代码节点里输出，不额外加节点 |
| 查询条件可以「可选」 | 条件写死（#6） | 过滤移到下游代码节点，不额外加节点 |
| 「变量聚合」节点做两路合并 | 两路直连结束节点即可 | **省** 1 个节点 |

**经验公式**：`实际节点 ≈ 施工图节点 + (动作数 − 2)`（每多一个动作多一个分流选择器）
`+ (需要查重 ? 3 : 0)`。

### 🔴 入参名 vs 上游变量名：**必须在构造期决定，事后改会被吃掉**

同一类坑在同一个项目里出现了三次，每次都是「跑完校验看着 0 error，实际静默丢东西」：

```python
# ❌ 三个库节点输出的变量名都叫 rowNum，照抄原名
[L.ref("100008", "rowNum", "integer"),
 L.ref("100011", "rowNum", "integer"),
 L.ref("100013", "rowNum", "integer")]      # → 后两条覆盖前一条，只剩最后一个

# ✅ 在构造时就把引用名改成互不相同的
def ref_named(block, var, name, typ="string", items=None):
    r = L.ref(block, var, typ, items=items); r["name"] = name; return r

ref_named("100008", "rowNum", "v_rownum_add", "integer")
ref_named("100011", "rowNum", "v_rownum_upd", "integer")
ref_named("100013", "rowNum", "v_rownum_off", "integer")
```

**为什么校验器抓不到**：`E5` 只查「`blockID` 存在 + 输出名存在」，不查**条数**。
同名入参被静默覆盖后，剩下的那条完全合法。

> 判据：**引用名用于「区分来源」，输出名用于「平台接线」。
> 一个输入只能有一个名字，所以在你把它放进 `items` 的那一刻就必须定下来。**

**同一类坑的另两种形态**（都出在 `iface()` 按 name 去重这件事上）：

| 形态 | 症状 |
|---|---|
| 入参名 ≠ 上游变量名（想改名） | 事后遍历 `node["data"]["inputs"]["inputParameters"]` 改 `name`，会被下一次 `iface` 覆盖回去 |
| 输入参数声明了但没接上游 | 运行时是 `None`，不是空串 —— 别指望 `if not x:` 之前它有默认 |

### ⚠️ 尚未实测、别当已知事实用的两条

- **多条件选择器**（一个 `branches[0].condition.conditions` 里放 2 条 condition、`logic` 为 AND）：
  **本项目从未实测过**，所有已粘贴样本都是单条件。要用先在空工作流单独验一次。
  降级替代：让代码节点先产出 `'Y'`/`'N'` 字符串标记，选择器只做**字符串相等**判断 ——
  稳定、可观测、端口语义明确，代价是 +1 个代码节点。
- **数组类字段的「长度大于 / 为空」运算符**：同理未实测。一律改用 Y/N 字符串标记。

> 判据：**宁可多一个 5 行代码节点，不要用一个没验证过的运算符。**

### 🔴 节点 id 在粘贴到画布后会被平台重发

**实测（2026-09-26）**：交付的 `100003 / 100006 / 100007`（三个数据库节点），
粘到画布后变成 `100037 / 166838 / 109165`。

**后果**：节点描述里若写「走到 100007『新增登记』」，用户粘完就对不上号了。

| 场景 | 怎么写 |
|---|---|
| JSON 内部的 `edges` / `ref.blockID` | ✅ **必须**用 id（这是机器读的） |
| 节点描述里**指代另一个节点** | ❌ 不要只写 id → ✅ 写**标题**（「走到『新增登记』」），可附 id 作参考 |

## ⚠️ 交付清单：JSON 之外还必须给什么

**这个技能最容易被漏掉的一节 —— 因为漏的东西恰恰是"JSON 里没有的"。**

### 事实：剪贴板信封不含工作流名称与描述

顶层只有 `type / source / json / bounds` **四个键**（已对 15 份自产文件逐一验证）。
`source` 里是 `workflowId / flowMode / spaceId / isDouyin / host`，**没有任何 name / description 字段**。

⇒ **粘贴只还原节点和连线。工作流的名称和描述必须在 Coze 新建弹窗里手填。**

### 所以每次交付工作流 JSON，必须额外附一张「名称与描述表」

| 要给的 | 格式 | 为什么 |
|---|---|---|
| **英文名称** | `wf_xxx_yyy` | Coze 工作流名称**只接受英文/数字/下划线**，中文不合法、**连字符 `-` 也不行** |
| **中文名称** | 给人看，用于核对 | 文件名可中文，但平台里必须是英文名 |
| **描述** | 一段话 | **不是备注，是路由依据**：Bot 挂多条工作流时，大模型**只按描述**判断调哪条 |

**三条写描述的规则**：
1. 写**触发场景**（学员会说什么、什么情况下该调它），不要写"本工作流用于处理XXX"。
2. 写**边界**（什么情况下**不该**调它、该交给谁）。
3. 描述同时给人看 —— 运维排查时它是唯一能快速判断"这条是干嘛的"的东西。

### 交付四要素（缺一项接手的人就无从下手）

| # | 要素 | 说明 |
|---|---|---|
| 1 | **工作流 JSON** | 可粘贴的单行文件 |
| 2 | **名称（英文）+ 中文名 + 描述** | 平台不给，必须手填 |
| 3 | **归属契约** | Owner / 创建位置 / 运行时挂载点 / 依赖 |
| 4 | **未配置项清单** | `validate_workflow.py` 的 `ℹ️` 段，告诉用户画布上要补什么 |

> **判据**：交付的是"这个东西在系统里的完整位置"，不是一个文件。
> JSON 是"东西"，名称/描述/归属/待补项是"位置"。**只交付文件 = 交付只做了一半。**

## 输入源可靠性分级（决定你能不能做，别浪费时间）

用户给的「学习材料 / 需求材料」形式差别极大。**先判断形式，再决定接不接**：

| 输入形式 | 能产出可粘贴工作流？ | 为什么 |
|---|---|---|
| 🥇 **画布 `Ctrl+A` → `Ctrl+C` 的剪贴板 JSON** | ✅ **能，无损** | 平台自己的序列化结果，字段齐全 |
| 🥈 **节点配置文档**（节点表 + 变量表 + 提示词，如 WF-8/WF-9） | ✅ 能 | 结构靠文档，资源 ID 用 `harvest_ids.py` 补 |
| 🥉 **单个已配置好的节点**（`Ctrl+C` 一个节点） | ✅ 能 | 用来补未知类型的编号与字段 |
| ⚠️ **需求表截图**（PRD / 功能矩阵 / Excel 截屏） | ✅ **能**（见 `references/12-…` §12.1） | 它给的是**业务语义**（角色/功能/红线/统计口径），不是平台结构 —— 与画布截图的可用性完全相反 |
| ❌ **画布截图 / 录屏** | ❌ **不能，物理上不可能** | 见下面的量化 |

> **别把两类截图混为一谈**：判断口诀是「图上是**文字需求**还是**节点方框**？」
> 文字需求 → 可接，先拆成「名称｜服务对象｜功能点｜业务规则｜统计口径」五元组；
> 节点方框 → 索要 `Ctrl+A → Ctrl+C` 的 JSON。整条链路见 `references/12-requirement-table-to-workflow.md`。

### 为什么截图不行（量化过，不是感觉）

1. **文字不可读**。实测一张 1920px 宽、装了 26 个节点的截图：每张节点卡只有 **91px 宽**，
   而真实节点卡是 **360px** → 缩放比约 **25%** → 真实 UI 里 14px 的标题在截图里只有 **3.5px 高**。
   放大只能插值，**不能创造信息**，8 倍放大也还是一团糊。
2. **资源 ID 根本不在图上**。以一份 35KB 的可粘贴载荷为例，各类信息占比：

   | 类别 | 占比 | 截图能否提供 |
   |---|---|---|
   | 结构骨架（id / 类型 / 坐标 / 尺寸 / 连线） | 74.6% | 部分（类型只能到**色系**） |
   | 文字内容（标题 / 提示词 / 代码） | 21.6% | **完全不可** |
   | 变量引用（blockID + 变量名） | 3.3% | **完全不可** |
   | 平台资源 ID（库表 / 字段 / 知识库 / 模型） | **0.4%** | **图上不存在** |

   **那 0.4% 是最致命的**：粘贴时平台会真的去查库/表/字段/知识库是否存在，查不到就阻断导入。
   所以**哪怕把 99.6% 全猜对，照样粘不上。**

3. **色系分不出类型**。实测按图标主色分类的结果：12 个「青绿系」节点里挤着
   代码 / 选择器 / 循环 / 批处理 / 变量聚合 / 意图识别 **6 种可能**，无法收敛。

### 截图唯一有用的场景

**需求沟通**：判断「这个工作流大概多少个节点、什么形态」。程序化检测卡片框可以数出节点个数、
读出左右顺序和上中下分层，用于理解结构意图 —— 但**不能作为生成的输入源**。

> 如果用户只给了**画布截图**，**直接说明上面这条，并索要 `Ctrl+A → Ctrl+C` 的 JSON 或节点配置文档**。
> 不要试图硬猜，猜出来的既粘不上又浪费时间。
> 但若给的是**需求表截图**，那是合法输入源，直接开工 —— 见 `references/12-requirement-table-to-workflow.md`。

## 交付前的固定动作

> **⛔ 第 0 条（最高优先级，2026-09-25 用户明确定下）：先出「搭建说明书」，确认后再转 JSON。**
> 不允许跳过说明书直接产 JSON。抽象层级必须写到「画布上下拉框选什么」的粒度。
> 详见本文件末尾同名章节。

1. **先挖真实资源 ID**：跑 `scripts/harvest_ids.py` 从用户已发布的工作流里挖 `databaseInfoID` / `fieldID` / 知识库 ID / 子工作流 ID。**不要用 `FILL_ME_*` 占位资源类 ID——平台在粘贴时会强校验，会直接弹红条阻断导入**（实测：`知识库 FILL_ME_xxx不存在`）。
2. **参数不全的节点 → 产出「空配置态」，不要编内容、也不要填空 ID**（见事实 5）。
   - 空数组 `[]` ✅ 能粘 ｜ `FILL_ME_*` ❌ 弹红条 ｜ `[{"databaseInfoID": ""}]` ❌ 畸形值
   - 用户没给提示词 / 意图名 / SQL → **留空**，交付时列进「未配置项」让他自己补。
3. **子工作流节点（type=9）有 4 个专属字段，缺一个就报 E14**（实测踩坑，2026-09-25）：
   ```json
   { "id": "100005", "type": "工作流", "title": "调 WF-04",
     "sub_workflow_id": "7689300536088346665",     // ← 不是 workflow_id
     "sub_workflow_version": "v0.0.1",              // ★ 必须是 "v0.0.1" 这种格式，不是 "1"（2026-09-25 实测修正）
     "sub_space_id": "7495957404262121481",
     "input_defs": [ {"name":"in_query","type":"string","required":true}, ... ],
     "inputs": { "in_query": "100001.in_query", "biz_type": {"value":"答疑","type":"string"} } }
   ```
   **🔴 `sub_workflow_version` 格式（2026-09-25 用户回传真实节点的实测）**：
   平台上真实值长这样 —— `"workflowVersion": "v0.0.1"`（带 `v` 前缀 + 三段版本号）。
   写成 `"1"` 时**不报错、能粘贴**，但子工作流节点在画布上显示**未绑定**（要手动重选一次）。
   回传的另一处证据是 `_temp.externalData` 里的 `flow_version: "v0.0.1"` / `latestVersion: "v0.0.1"`，
   两处一致 → 这就是真值。**判据：只要节点是「发布成功过」的，版本号一律写 `"v0.0.1"`。**
   同一次实测还确认了 `inputs.type = 0`（整数 0）与 `inputs.spaceId` 必须写。
   **`input_defs`（声明）与 `inputs`（传值）是两回事，必须同时给**：
   - 生成器只把 `inputs` 展开成 `inputParameters`；`inputDefs` 只从 `input_defs` 读。
   - 校验器 E14 拿两者做**集合比对**：`input_defs` 声明了但 `inputs` 没传 → 报「入参 X 未传值」；
     反过来 `inputs` 传了但 `input_defs` 没声明 → 报「inputParameters 里多出 X」。
   - **只给 `inputs` 不给 `input_defs` 的典型症状**：同时报「多出入参」+「缺少 workflowId」（其实是键名写错）。
   - `input_defs` 的入参名/类型/必填，必须**照抄子工作流开始节点的真实 outputs**（用 `harvest_ids.py` 或读其回传 JSON 确认），
     写错名字平台不报错，但运行时取不到值。
4. 跑 `validate_workflow.py`，**0 error 才交付**。七个硬门槛：
   - `E16`：**顶层 `bounds` 必须存在** —— 缺了粘贴「毫无反应」且**没有任何报错提示**，最难查。
     （技能自带的冒烟测试文件曾犯过这个错，见 `references/12-…` §12.9 翻车 2）
   - **`E17`：根层节点必须从「开始」可达** —— 不可达的节点**永远不会执行**且不报错，
     画布上看着完全正常。判据是**可达性（BFS）**，不是「出现在某条边里」：
     只漏入边、出边还在的节点，用「出现在边里」会漏判（实测过）。
   - **`E18`：意图识别的出边必须连完整** —— `N 个 intents → branch_0…branch_{N-1} + default`，
     一条都不能少。这是**画布上肉眼可见**的缺陷（分支端口悬空），用户会直接指出来。
   - **`E19`：数据库字段的三种写法** —— `fieldList.fieldID`=**数字**、`conditionList.left`=**字段名**、
     `fieldInfo.fieldID`=**字符串**。三者故意不同，别「统一」。写错的表现是画布上
     整列 `undefined` / 条件左侧显示裸数字（不报错、能粘贴）。
   - `E15`：资源类 ID 不能是 `FILL_ME_*` 占位（平台粘贴时强校验，会弹红条）。
   - `W19`：**提示词里的 `{{变量}}` 必须在本节点 `inputParameters` 里存在** —— 平台不报错，但运行时取不到值。命中时**要在交付说明里点名文件与节点**。
   - **`G1`（只在「优化已有工作流」时生效）：交付前必须跑一遍「优化项自检清单」，每条承诺配一条机器断言，全部通过才交付。**
     校验器只查**结构是否合法**，查不出「某项优化整个消失了」——
     实测翻车：两条修复流水线各自都能跑通，后跑的那条只含部分步骤却直接从原始文件覆盖产物，
     于是 6 项语义优化被**静默回退**，而文件名不变、校验器仍 `error 0`、`diff` 因为比错了方向也看不出来。
     **判据：交付说明里承诺了什么，就要有对应的机器断言；只写在文档里的优化项等于没做。**
     详见 `references/12-…` §12.16。
5. 交付时**同时给三样**：`out.json`（让用户 Ctrl+V 粘贴）+ 一份"节点清单表"（id / 类型 / 标题 / 状态）+ 一份"**待补清单**"（哪些节点是空配置态、哪些是代码占位、需要用户做什么）。

6. **★ 未配置态节点的 `description` 就是施工说明 —— 这是用户定的硬规则（2026-09-25）。**
   **JSON 里一律不写表名/表 ID/字段值**（`databaseInfoList: []`、`datasetList: []`），
   但**描述里必须写全「填什么、填到哪」**，用户在画布上点开节点就能照着配。

   **数据库节点统一四段式**（缺一段用户就会漏配）：
   ```
   【写入目标】<表名>（<表的中文用途>）      ← 查询节点写【查询目标】
   【操作】新增一行 / 更新 / 查询
   【查询条件】<字段> 等于 <引用>            ← 查询节点写这条
   【更新条件】<字段> 等于 <引用>            ← 更新节点写这条
   【字段清单】                             ← 新增/更新节点写这条
     · <字段名>  ← <引用来源 或 固定值>
   【说明】本节点为未配置态，粘到画布后<要做什么>
   ```
   **知识库节点两段式**：`【检索目标】<库名>` + `【输入】query ← <引用>` + `【建议参数】TopK/匹配度/改写`。

   ★ 好处（已实测）：用户不必对着聊天记录翻，**施工信息跟着节点走**；
   而且 `description` 是剪贴板 JSON 的一部分，**粘贴后不会丢**。

   实体引用一律写成 `节点id.变量名`（如 `100001.in_query`），不要写「开始节点的问题字段」
   ——画布上找得到的是 id 和变量名，中文标题可能有歧义。

7. **输出一律单行紧凑**（`build_workflow.py` 默认如此，且**已自动带顶层 `bounds`**）。**缩进版体积翻倍，实测会导致粘贴「毫无反应」。**
   写文件还要 `newline="\n"`，避免 Windows 写出 `\r\n`。
8. 告知用户粘贴方式：打开工作流画布 → **Ctrl+V**（会自动覆盖原有的开始/结束节点参数）；会员也可用「导入」按钮选文件。
   ⚠️ **粘第二次会毫无反应** —— 画布上已有这些 node id 时，平台静默忽略。要么新建空工作流，要么先删掉已有节点，要么换一批 id。
9. 如果用户反馈「毫无反应」，**第一个怀疑对象永远是顶层 `bounds`**，而不是 id 冲突 / 体积 / 平台限制。
   最快的自证方法：拿平台自己导出的、**能粘**的文件，**删掉顶层 `bounds`** 再让用户粘 —— 如果它也变得毫无反应，就实锤了。
10. 交付时**顺带给一个 3 节点的冒烟测试文件**（开始→代码→结束，约 3KB）。它能粘进去说明通道没问题，粘不进去就是焦点/剪贴板/权限问题 —— 比一上来查 JSON 结构快得多。
   ⚠️ **这个文件本身也必须过 `E16`**。它缺顶层 `bounds` 时会「毫无反应」，于是从诊断工具变成误导工具 ——
   用户会以为「平台禁止外部 JSON」，而其实别的文件都能粘。来源：`assets/smoke_test_3nodes.json`
   （由 `assets/specs/smoke_test.json` 经 `build_workflow.py` 生成；**改内容改规格再重生成，不要手改产物**）。
11. 提醒用户：**粘贴后需要自己拖拽连线是常见现象**（合成粘贴有时不还原边），以及**改了工作流必须重新发布**才生效；**子工作流必须先发布**，否则调用方选不到它。

## ⚠️ 用户回传粘贴结果后，必查的 5 类「静默失败」+ 一类生成期埋雷

粘贴成功 ≠ 工作流能跑。**以下 4 类问题不报错、画布看着正常，但运行时默默产出错误结果**。
拿到用户 `Ctrl+A/Ctrl+C` 的回传 JSON 后，**逐项机器核对**（脚本见 `_工具/extract_from_paste.py`）：

| # | 检查项 | 症状（回传里长什么样） | 为什么危险 |
|---|---|---|---|
| **1** | **子工作流节点 `inputParameters` 为空** | `inputDefs` 有 4 个名字，`inputParameters` 是 `[]` | 子工作流收到全空入参 → 往库里写空记录。**实测踩过（2026-09-25 WF-03）** |
| **2** | **数据库节点 `fieldValue` 全空** | `fieldInfo` 里 fieldID 有值、`fieldValue.content` 是 `""` | 插入一行空数据；不报错 |
| **3** | **更新节点缺 `fieldList`** | `updateParam` 只有 `condition` 一个键 | 运行时什么都不改，静默失败 |
| **4** | **数据库节点 `conditionList` 是 `[[null,null,null]]`** | 三连 null | 查询永远查不到 / 更新匹配不到任何行 |
| **5** | **引用了表里不存在的字段名** | 节点里 `fieldInfo.fieldID` 有值但**字段名对不上表**；用户在画布上「找不到这个字段」 | 配不出来 / 写空值。**实测踩过（2026-09-25 WF-08 的 `fingerprint`、`session_id`）** |
| **6** | **★ 字段「映射对了但引用错了上游」** | fieldID 正确、值也非空，但 `fieldValue` 引的是**另一个节点的同名/近义输出** | 写进去的永远是错的数据，**不报错、字段非空、日志看着正常**。**实测踩过（2026-09-25 WF-14）** |

**第 6 类的真实案例（最值得警惕的一种）**：

WF-14 的 `qa_log` 写入节点里，`answer` 字段（fieldID `1833231909893`）的引用指向了
**子工作流节点 WF-15 的 `out_answer`**（那是"我没查到，已记下来"的兜底话术），
而正确来源应该是 `100007.final_answer`（本工作流拼好的真实答案）。

**症状**：`answer` 字段**永远非空**、永远有值、写库成功、校验器 `error 0` ——
但从功能上看，**不管问题有没有命中知识库，日志里存的都是那句兜底话术，真实答案全丢了**。
这类 bug **只能靠「人工读一遍引用的语义对不对」发现**，工具查不出来。

**排查手法**：拿到回传后，**逐字段问一句「这个字段引的那个变量，真的是它该引的吗？」**
特别注意**名字相近的节点**（`out_answer` vs `final_answer`、`in_query` vs `question`）。
判据：**如果两个节点的输出语义不同，而字段引了错的那个，就是这类 bug。**
正确做法是**统一走同一个"装配节点"的输出**，不要让数据库节点从多个节点各引各的
（WF-14 修法：7 个字段全部改引 `100007` 一个节点的输出）。


### ⚠️ 6 类之外，最贵的一类：**字段名/枚举值「凭印象写」**

上面 5 类是「回传里能看出来的」，这一类是**生成阶段就埋下的**，回传里看不出来、校验器也查不出：

| 坑 | 实测案例 | 为什么查不出来 |
|---|---|---|
| **字段名不存在** | WF-08 spec 写 `fingerprint` 查重、写 `session_id` 入库，实际 `question_bank` 14 列里两个都没有 | 校验器只查 JSON 自洽性，**不知道真实表结构**。用户在画布上选不到字段才发现 |
| **枚举值差一个字** | spec 写 `review_status = 已审核`，表的合法值是 **`已通过`** | **不报错、不崩溃、永远查不到数据**。用户会误判成「题库里没题」 |

**根治法（强制动作）**：写任何数据库节点的字段名 / 枚举值之前，
**必须先读「单一事实来源」**——本项目的 `06_共享资源/数据库/schema.sql` 与
`数据库设计说明与建表指令.md`。**不允许从工作流 JSON 反推、不允许凭印象写。**

**交付前自检（脚本次之，规则优先）**：
- 枚举类字段（`status` / `type` / `*_status`）→ 去建表文档里逐字复制取值，**绝不手打**
- 字段名 → 与 `schema.sql` 的 `` `列名` `` 逐字对照
- 建表指令里写了「不要创建 id 字段」之类的排除项 → 也要照着排除（这类字段平台真的不会生成）

## 🔴 粘贴通道本身会「静默丢节点」（2026-09-26 实测，两次实验）

**症状**：整段粘 13 节点 / 13 连线的 JSON，画布上只出现 **11 个节点、0 条连线**。
**不报错、无提示**，粘完像什么都没发生。且**连线全灭** —— 只要有一个节点没下来，
所有边（包括幸存节点之间的）都建不起来（推测边是在节点之后统一应用的）。

**已证伪的假设（别再从头试）**：

| 假设 | 证伪证据 |
|---|---|
| 文件里没写连线 | 文件 13 条边两端齐全 |
| 边键名错 | 键名就是 `sourceNodeID` / `targetNodeID` / `sourcePortID`（**不是** `source`/`target`，查边用这三个键） |
| 节点结构缺键 | 丢的和存的代码节点 `data`/`inputs` 键集合完全一致 |
| 代码 >2048 字节被截 | 4233 字节的代码节点存活，2405 / 3187 字节的被丢 |
| 控制字符 / BOM / 零宽 | 全文件扫描 0 命中 |
| **节点 id 与画布已有节点撞车** | id 全段重排（`1000xx`→`7001xx`）后粘空画布，**丢的还是同样两个** |
| 代码体积本身 | 见上，大小与存活无相关性 |
| 代码含中文注释 + 空行 | 压缩到 0 注释 0 空行重粘，缺口不变 |
| 整包信息量太大 / 粘贴动作问题 | 切包实验：A 包(7节点)✅ C 包(4节点)✅，B 包(恰好那两个节点)❌ |

**根因（✅ 已真机证实，2026-09-26 第四次实验：修复版整包 13 节点 / 13 连线全到位）**：

🔴 **代码节点 outputs 用 `"type": "number"`，平台剪贴板解析器不认 → 节点被静默丢弃。**

证据链（三步递进，后两步是同一轮排错里攒出来的）：
1. 切包对照实验 A✅ C✅ B❌ —— 一次性证伪「整包太大/粘贴动作」并缩到 2 个节点。
2. 全库 22 个代码节点全景对照：20 个活节点 0 个含 number，唯二含 number 的正是被丢的；
   输出数 / 描述长度 / 代码体积全被活节点覆盖，**number 是唯一 22/22 分离特征**。
3. 用户回传的 4 份真实画布 JSON 全量类型词表 = `string/integer/list/object/ref`，
   **平台自己从不写 number**；且结束节点（type 2）带 number 能存活 —— 只有代码节点校验最严。

**修法（生成阶段直接规避，不用等粘失败）**：
1. **出参类型词表**：代码节点 outputs 只用
   `string / integer / boolean / list / object`；**`number` 一律禁止**。
   要小数就在代码里 `int(round(x))` 后声明 `integer`
   （`grading_log.ai_score` 是 DECIMAL(6,1)，损 0.5 精度可接受）。
2. **整包不需要预先切包**：13 节点整包已证实能正常粘成。
   切包只是**定位手段** —— 粘不进时按上下游切 2~4 包逐个试，哪包粘不进毒就在那包里。
3. **手动兜底（最后手段）**：入参/出参/代码全文写成 txt 让用户手动建
   （UI 出参类型选 Integer，别选 Number）。

**出包前自检**：`grep '"number"' 交付.json` 必须 0 命中。

**排错方法论**（这次值 30 分钟的经验）：
- **查边用 `sourceNodeID`/`targetNodeID`/`sourcePortID`** —— 用 `source`/`target` 读会全得到 None，
  把「文件完好」误判成「没连线」。
- **假设必须标注验证状态**。「有证据的推断」（如 id 撞车：11 个 id 一字未改、独缺两个）
  一次真机实验就能证伪。下判断时同时想好「证伪后下一个嫌疑是谁」，
  并把排除表写进文档 —— 否则过两天同样的嫌疑会重新被查一遍。
- **现象本身指认机制**：「只有两个节点丢、其余 id 一字未改」比「文件坏了」信息量大得多，
  先问「什么机制能造出这个现象」，再动手改。

## ⚠️⚠️ 最重要的一条：**spec 的抽象层级不够，平台会自己猜，猜错了就要人来修**

**实测踩过（2026-09-25，反复返工三轮才定位）**：spec 里写

```json
"inputs": { "item_list": "100002.item_list", "result": "100003.result" },
"query": { "left": "fingerprint", "right": "100002.fp_list" }
```

这一层只表达了「**谁引用谁**」，**表达不了**：
- 平台下拉里该选哪个输出（`item_list` 还是 `fp_list`）
- 运算符该选什么（平台的真实运算符见下方「运算符完整清单」）
- 值的类型是什么

**结果**：粘贴后平台把 `fingerprint` 的右值自动填成了 `item_list`（一整个对象数组），
类型不匹配、语义也错。用户在画布上看到"类型都不一致"，只能手工纠 —— 改了这边那边又错位，
**永远修不完**。

### 正解：**先写「搭建说明书」，再由说明书转 JSON**

**用户明确要求的工作流**（2026-09-25 定下）：

> 每条工作流都必须先产出**完整搭建说明书**（含前驱/后驱节点、变量名及类型、
> 系统提示词、用户提示词、逐项配置取值）→ 用户照单在画布上配 → **再转 JSON**。
> 不允许跳过说明书直接产 JSON。

**说明书模板**（`00_方案与需求/搭建说明书/WF-XX_xxx_搭建说明书.md`）：

```
# WF-XX xxx · 搭建说明书
## ⚠️ 开工前必读：三条平台事实
## 〇、前置条件（表结构逐列列出）
## 一、节点表（序号 | 节点ID | 节点名 | 类型 | 前驱 | 后驱）
## 二、画布连线表（从 | 从哪个口 | 到 | 到哪个口）
## 三、逐个节点详细配置
## 四、搭完后的自检清单 + 试运行假数据 + 反证测试
## 五、对外契约（入参/出参变量名+类型+必填）
## 六、依赖顺序
```

**每个节点必须写全**：
1. **输入变量表**：变量名 | 类型 | 引用来源（写「节点X → 输出Y」）
2. **输出变量表**：变量名 | 类型 | 谁在用
3. **代码全文**（代码节点）
4. **提示词原文**（大模型节点：系统提示词 + 用户提示词分开写）
5. **数据库配置逐项**（表 / 查询字段 / 每行条件的左值·运算符·右值类型·右值引用 / 上限 / 输出）

**每条引用必须写全三件事**，缺一不可：
> **源节点 · 输出名（要精确到 `fp_list` 而非 `item_list`）· 运算符（要用平台真实词，见下方清单）**

### ★★ 查询运算符完整清单（2026-09-25 官方文档核实，**推翻早期「只有 4 个」的错误说法**）

官方文档 `open/docs/guides/database_select_node` 明文列出的运算符**共 8 个**：

| 运算符 | SQL 等价 | 备注 |
|---|---|---|
| 等于 | `=` | 早期就掌握 |
| 不等于 | `!=` / `<>` | **早期遗漏** |
| 模糊匹配 | `LIKE` | 后端自动加 `%值%`，**不用手写通配符** |
| 模糊不匹配 | `NOT LIKE` | **早期遗漏** |
| **包含** | **`IN`** | **早期错误地断言「平台没有 IN」—— 实际原生支持** |
| 不包含 | `NOT IN` | **早期遗漏** |
| 为空 | `IS NULL` | 早期掌握 |
| 不为空 | `IS NOT NULL` | **早期遗漏** |

**⚠️ 确实没有的**：区间比较（`>` `>=` `<` `<=` `BETWEEN`）。
所以「按时间区间查」**仍然配不出来** —— 这条早期判断是对的，替代方案（拉全量 + 代码过滤）依然有效。

**查询上限**：默认 **100**，**最大 1000**（官方明文）。早期不确定上限时**不要编数字**。

**排序**：支持多字段，可拖动调整优先级；按字段类型给出 Z→A / 9→0 / 1→0 等选项。

> 🔴 **教训（很贵）**：早期版本的技能里写了「平台上根本没有 `包含于`，只有 等于/属于/模糊匹配/为空」
> 并据此让方案「绕路」（把 `fingerprint IN [...]` 退化成逐条查）。**该断言是错的，导致下游方案做了无用功。**
> **根因：把「我在画布上见过 4 组」当成了「平台只有 4 个」，没有去查官方文档。**
> **判据沉淀：凡是写进交付物的「平台不支持 X」，必须有官方文档或实测证据；否则只能写「未验证」。**

### 硬规则

| 规则 | 说明 |
|---|---|
| **抽象层级要写到"下拉框选什么"** | 不能停在"谁引用谁"。凡是要在画布上点的，说明书里都要写出**逐字取值** |
| **运算符只用官方清单里的 8 个** | 等于/不等于/模糊匹配/模糊不匹配/包含/不包含/为空/不为空 —— 区间比较确实没有 |
| **数组匹配用「包含(IN)」** | 右值类型选「引用」，指向**字符串数组**（不是对象数组） |
| **粘贴后必须留核对步骤** | 说明书里要写「粘完对着这三项逐个看」，因为平台不完美还原引用 |
| **给换路方案** | 平台能力不确定时（如"能不能展开 object 的键"），给出做法 A / 做法 B，**别让用户卡住** |

### 反模式（不要做）

- ❌ 只给 JSON，让用户在画布上"照着理解"→ 必然返工
- ❌ 在描述里写"引用 `100002.cond.subject`"但不说平台上怎么点出来 → 用户配不出来
- ❌ 假设平台有某个运算符 / 某个引用能力，不验证 → 用户发现配不出来才反馈
- ❌ 修一个补一个，不回头统一抽象层级 → **修来修去修不完**（用户原话）
- ❌ **★ 用户说「不好用」时先辩解「新方案更优雅」** —— 见下方「架构优化被否决」的反面教材

> 判据一句话：**凡是「字段名 / 枚举值」，都必须是复制来的，不是打出来的。**

### ★★ 反面教材：不要用「架构更优雅」说服用户换掉能跑的东西（2026-09-25 实测翻车）

**背景**：WF-15（教务未命中转存）画布上有 9 节点版（自己查重/新增/更新）。
我另做了个 5 节点版（只打标 → 调 WF-04 复用登记 → 包话术），理由是「查重逻辑不重复实现」。

**用户反馈**：「我复制你的 WF-15 就俩四个节点，还断开了。**还不如我现在的**」

**我的第一反应是错的** —— 我准备解释「新版架构更好、依赖 WF-04 是设计意图」。
**正确反应是承认用户对**：用户要的是能用的东西，不是更 DRY 的东西。

**为什么 5 节点版被否**：
1. **与画布现状差异太大** —— 9 → 5，视觉上像「缺了一半、连线断了」，用户第一眼就不信任。
2. **迁移成本 > 收益** —— 老版能独立跑，新版强依赖 WF-04 已发布。用户没有动机换。
3. **DRY 的收益是「未来改一处生效全线」** —— 但项目当前阶段是**打通链路**，
   不是优化维护性。**优化错了阶段 = 负收益。**

**沉淀成三条判据**：

| 判据 | 说明 |
|---|---|
| **① 先问「现值有硬伤吗」** | 如果用户现有结构能跑、没有功能性缺陷，**不要动它**。哪怕你的方案更优雅。 |
| **② 方案要求用户「删掉现有可用结构」时，默认否决** | 除非能指出当前结构的具体 bug 或明确损失。提方案时必须**先说清迁移代价**。 |
| **③ 节点数差异大时，先想「用户会不会觉得缺了东西」** | 9→5 这种减法，用户会本能怀疑。要换，就得在交付说明里**主动解释为什么少是对的**，而不是等用户来问。 |

**同一功能的两个版本并存 = bug 温床**：当时 WF-15 的新旧两版 spec 同时存在，
导致连我自己都分不清画布上是哪个。**做替代方案时必须立刻归档弃用版本**
（做法：改名 `_archive_XXX.spec.json` 移出 `specs/`，或直接删）。

**额外收获（同一份回传可挖出）**：
- `commit_id` / `plugin_id` 出现 → **说明该子工作流已发布**，下游可以放心引用。
- 开始节点 `outputs` → 直接就是下游 spec `input_defs` 的真值来源，**照抄，别手写**。
- 数据库节点 `databaseInfoList` 的 `databaseInfoID` + `insertParam.fieldInfo` 的 fieldID 列表
  → **能反推表的真实列数**。两次回传同一张表的 fieldID 若完全一致，说明列数就是那么多，
  **不要再猜「平台是不是少列了几个」**（实测踩过：设计 8 字段、表实际 7 列）。
- **★ 回传「功能正常的那一条」= 拿到一份「正确配置范本」。** 用户回传已发布的 WF-04 后，
  我把它跟 WF-15 逐字段比对，直接看出 WF-15 的条件写错了（`subject` vs `normalized_key`）。
  **做法：让用户优先回传「已经跑通的那条」，用它的配置当基准去校验其他条。**

### ★★ fieldID「递推破译法」—— 2026-09-25 实证，推翻「fieldID 无法凭空生成」

`references/04-node-schemas.md` 说 fieldID「只能从画布上配一次再复制出来，**无法凭空生成**」。
**这句话只对了一半**：单看一个孤立的 fieldID 确实无从生成，但**只要拿到同一张表的多个 fieldID，
就能用「位置 + 递推」把剩下的全部推出来**。方法如下（已在 `qa_log` 上完整验证）：

**第 1 步：从回传节点里抽出「fieldID → 引用来源」的配对。**
用户在画布上配过的节点，每个 `fieldInfo` 项都带 fieldID 和一个 `fieldValue` 引用。
引用来源的**变量名**通常就是字段名的强提示（如引 `100001.session_id` → 该 fieldID 必是 `session_id`）。

**第 2 步：按 fieldID 数值排序，跟说明书里的建表列序对齐。**
fieldID 是**按建表顺序递增分配**的。把实测到的若干 ID 排成一列，与文档里的列顺序对照，
**位置吻合的即可确认字段名**。

**第 3 步：找缺口。**
实测 ID 往往是连号的，中间跳过的号就是「建过但没被映射」的列。
**把缺口的位置与「文档里有、但样本里没映射」的列名一一对应** —— 若缺口数与未映射列数相等、
且位置顺序完全吻合，**递推即成立**。

**实例（`qa_log`，2026-09-25 验证）**：

| 实测 fieldID | 对应列（据引用来源） | 未映射缺口 |
|---|---|---|
| `…889` | `session_id` | |
| `…890` | `subject` | |
| | | **892 → 891 缺** |
| `…892` | `question` | |
| `…893` | `answer` | |
| | | **895 → 894 缺** |
| `…895` | `hit_kb`（boolean ✓） | |
| | | **897 → 896 缺** |
| `…897` | `created_at`（integer ✓） | |

说明书 1.2 列的 `qa_log` 是 9 列，样本只映射了 6 列，未映射的是 `grade`(第3)、`q_type`(第6)、`kb_source`(第8)。
**缺口 3 个 = 未映射列 3 个，且位置顺序一一对应** → 于是推定：
`891=grade`、`894=q_type`、**`896=kb_source`**。

**交叉验证（必做，别省）**：拿 `fieldValue` 的 `input.type` 反查 ——
`hit_kb` 的 type 是 `boolean`、`created_at` 是 `integer`，与文档标注的类型吻合，
说明「ID → 列」的映射方向没搞反。**类型对得上，递推才可信。**

**什么时候不能递推**：① 只拿到 1 个 fieldID（无位置信息）② 缺口数与未映射列数对不上
（说明中间建了又删的列）③ 文档里的列序本身不可靠。这三种情况一律**回去要更多样本**，
不要赌。**递推出来的值要在 `coze_ids.json` 里标 `"verified": false`**，与实测的 `true` 区分开。

### ★★ 「一次回传解锁一张表」—— 主动向用户索取样本的正确姿势

**卡点是「拿不到 fieldID」，不是「配不出来」。** 用户手上有现成的、已配好的画布节点，
但**不会主动想到要复制给你**。所以要做的是**把索取变成一件 10 秒的具体动作**，
并明确告诉他**复制哪一个**。

**做法（2026-09-25 实操，效果最好）**：写一份**取证清单**，四列表格：

| 打开哪个工作流 | 复制哪个节点 | 能解锁什么 |
|---|---|---|
| WF-13 批改历史查询（3 节点，最小） | 点一下「查 grading_log」节点 → `Ctrl+C` | `grading_log` 12 列 → 解锁 WF-12/13 |
| WF-09 题库查询 | 点一下「查已通过题」节点 → `Ctrl+C` | `question_bank` 14 列 → 解锁 WF-08/09 |

**四条铁律**：
1. **"复制哪个节点"必须具体到节点标题** —— 不说"给我个数据库节点"，要说"点一下『查 grading_log』那个框"。
   用户面对 29 个节点时，"随便给一个"= 他不动。
2. **优先挑节点最少的那条工作流** —— 3 节点的流最容易找到目标节点。让用户先做最省事的，建立正反馈。
3. **说清成功的样子** —— "粘出来是一长串 `{"type":"..."` 开头的 JSON；如果只有几个字，说明没选中，重来"。
   不然用户会复制到节点标题那段文字，然后以为成功了。
4. **讲清代价和收益** —— "1 次复制 → 我破译 → 剩下的 N 个节点全自动配好，你再也不用一个个手点"。
   用户对"能省掉多少次手点"最敏感。

**一个节点 = 一整张表**：只要那一个节点映射了 ≥3 个字段，就能用递推法推出全表。
所以**不要按"每个字段要一个样本"去要**，那会让用户崩溃。**要点是：一份回传 = 一张表 = 几个下游节点。**

> ### 🔴🔴 2026-09-26 更新：这条取证路线**已被用户明确否决，别再走**
>
> 用户原话：「**我不需要你写好数据库字段啥的，我只需要你给一份完整的工作流**，
> 如果字段不完整，你在描述里写清楚怎么配置就行了，我自己来配置，你只要能配置其他节点就行了。」
>
> 原因不是技术做不到，是**价值不对等**：
> - 破译 fieldID 要用户反复回传（每份回传 10 秒，但来回几轮、上下文全乱）；
> - 而字段映射这件事，用户**在画布上点一遍只要 30 秒**，比回传 + 等待更快。
> - 更关键：我猜出来的 fieldID 即使格式对，也可能被平台静默忽略（选不到列 / 少一列），
>   **错的配置比没有配置更糟** —— 没有配置只是"要你手点"，错配置是"你以为好了、其实数据是空的"。
>
> **正确做法（已落地到 `_工具/strip_db_config.py`）**：
> 1. JSON 里**不写任何字段级配置**（`fieldList` / `fieldInfo[].fieldID` / `databaseInfoList[].databaseInfoID` 一律留空或不输出）；
> 2. 节点描述里**写全**：表名、操作类型、条件（字段+运算符+值引用）、字段清单（字段名←引用来源）、枚举陷阱、注意事项；
> 3. **保留 `databaseInfoID`（表已选好）**，这才是有价值的注入 —— 它只消一次点击；
> 4. 描述尾部统一加「⬇⬇ 粘到画布后怎么配」的操作步骤。
>
> **判断标准**：交付物里"需要用户手点的项目数"应该尽量少且**可一眼看懂**，
> 而不是追求"零手填"。**零手填如果代价是反复打断用户，那不是交付质量。**
>
> ⚠️ 反过来说：如果某天用户主动问"能不能帮我配好字段"，再重启这条路线。
> **用户说了不要，就别再拿"为了你好"当理由反复重试。**

## 🔴 铁律 5（2026-09-25 反面案例）：索取时必须写「勾一个字段」这个动作

**回传了一份节点，却只解冻了表 ID、没解冻任何字段 ID。** 原因是：

- 查询节点（type 43）**一个查询字段都不勾**时，剪贴板 JSON 里
  **根本没有 `selectParam.fieldList` 这个键**（平台用"缺键"表示"返回全字段"）。
- 于是那份回传里 `fieldList` 是空的 → 一个 `fieldID` 都拿不到 → 递推法无从下手。
- 而 `databaseInfoList[0].databaseInfoID` 照样在 → **表 ID 拿到了，字段 ID 全没拿到**。

**所以索取话术要改成**：

> 复制前请先在节点里**勾上任意一个查询字段**（建议勾时间列 `created_at`），
> 这样 JSON 里才会带出 `fieldList` 和它的 `fieldID`。一个字段都没勾的节点，
> 我拿不到任何字段 ID。

**收料后的第一个检查动作**：`jsonpath $..fieldList` 非空吗？空就**当场告诉用户"这次没解锁成功，
要重勾一个字段再复制"**，而不是把半成品写进台账、事后才发现问题。
判据：`"fieldList" in selectParam` 且长度 ≥1。

**推论**：这份回传反而带来一个正向结论 —— **"查询节点不写 fieldList" 是合法且常见的形态**，
生成的 JSON 里如果塞 `"fieldList": []`（空数组），语义与"缺键"不同（数组 = 只要 0 个字段），
粘贴后可能返回空列表。**空数组要省略键，不要输出 `[]`。**

### ★★ 「能生成」≠「能交付」—— 多落点产物必须显式同步（2026-09-25 事故）

用户问「你没给我 WF-13」。查下来是**两处缺陷叠加**：

**缺陷 1：文件名里的两个数字含义不同，用户按编号找，被前缀数字误导。**
`09_WF-13_批改历史查询.json` —— `09` 是粘贴顺序，`13` 才是 WF 编号。
14 个文件里 12 个两者不等。**文件名里出现两个不同含义的数字 = 必现的可用性缺陷。**

> 修法：把含义写进名字本身 —— **`粘贴顺序09_WF-13_批改历史查询.json`**。
> 并在 README 里加一张「按 WF 编号速查表」，教用户"直接搜 `WF-13` 这三个字符"。

**缺陷 2（更严重）：产物存在多个目录，同步链断了。**

```
<agent>/工作流/产物/WF-xx.json    ← 生成器真正写到这里（N 个 agent 各一份）
99_交付文档/按顺序粘贴_01到18/      ← 用户取货在这里（第 N+1 处）
```

生成器**没有问题**（单独 build 出来的 WF-06，9 个字段 ID、条件、排序全在），
但交付目录那份停留在更早的时间戳、数据库节点全是空配置。**用户拿到的一直是空壳。**

**三条硬规则**：

| 规则 | 说明 |
|---|---|
| **有多个落点就要有同步步骤** | 不能假设"我 build 过了 = 用户拿得到"。同步必须是流水线里显式的一步 |
| **同步后要做一致性断言** | 不是"命令跑完没报错"就算完 —— 要比对源与目标的关键字段（如 fieldList 长度） |
| **清理垃圾别用正则猜命名** | 用「不在本次目标名单里的文件一律删掉」。正则一改命名格式就残留（本次残留过 3 个） |

> **判据**：如果用户说「你没给我 XX」「XX 是空的」，**先别急着解释，先核对文件时间戳与内容**。
> 十有八九是拿到了旧版本。同理，README 里一切"N 条零手填 / N 个未配置"的统计数字，
> **都必须由脚本扫产物得出，不许凭记忆写** —— 本次就靠脚本纠正了两个错数（5→8、12→8）。

**写扫描判据时的坑**：不同节点类型的配置字段路径不同，用错路径会误报。
```
43 查询 → selectParam.fieldList / selectParam.condition.conditionList
46 新增 → insertParam.fieldInfo
42 更新 → updateParam.fieldInfo + updateParam.condition.conditionList
```
另外要区分**「缺配置」和「故意不配」**（例如"无 where、拉全量"是设计意图），
否则会凭空多出一堆不存在的待办。

## 🔴 铁律 6：大模型节点的「用户提示词」必须显式写进 llmParam 的 `prompt`

**症状**：粘到画布的大模型节点，系统提示词有、用户提示词为空 → 节点能跑但输出瞎写。

**根因（生成器侧）**：`_llm_param` 构造 `llmParam` 时用的 bag 字典里，
有 `systemPrompt` 对应 spec 的 `system_prompt`，**但没有 `prompt` 这一项** →
永远落回默认值 `""`。spec 里写了 `user_prompt` 也没人读。

**修复**（`_工具/coze_node_lib.py` 的 `_llm_param`）：
```python
"prompt": (kw.get("user_prompt", ""), "string", 1),   # ← 必须加，否则用户提示词静默丢失
"systemPrompt": (kw.get("system_prompt", ""), "string", 1),
```

**自检代码**（改完必跑，别只看有没有这个键、要看内容长度）：
```python
for p in node["data"]["inputs"]["llmParam"]:
    if p["name"] in ("prompt", "systemPrompt"):
        print(p["name"], len(p["input"]["value"].get("content", "")))
```
期望：`prompt` 长度 > 0 且等于文档里那段提示词的字符数。

⚠️ **同类陷阱：先确认字段在哪一层，再下结论。**
`llmParam` 在 `node["data"]["inputs"]["llmParam"]`，
不在 `node["data"]["llmParam"]`。用错层级会得到 `None`，
很容易误判成「整个 llmParam 丢了」，然后去改根本不存在的东西。

**llmParam 的 19 个固定键**（缺一个平台会按默认值覆盖，其中 `prompt` 最容易漏）：
modelType / modleName(平台拼错) / generationDiversity / frequencyPenalty / maxTokens /
spCurrentTime / spAntiLeak / responseFormat / parameters / **prompt** /
enableChatHistory / chatHistoryRound / systemPrompt / stableSystemPrompt / canContinue /
loopPromptVersion / loopPromptName / loopPromptId

## 🔴 铁律 7：循环节点的连线端口（2026-09-26 实测校验器抓出）

循环（type 21）的连线分三层，端口名**固定**，写错校验器报 W11：

1. **内层入口线**（在循环节点的 `inner_edges` 里）：
   循环节点 → 循环体内第一个块，必须带 `sourcePortID="loop-function-inline-output"`
2. **内层出口线**（也在 `inner_edges` 里）：
   循环体内最后一个块 → 循环节点，必须带 `targetPortID="loop-function-inline-input"`
3. **根层出边**（顶层 edges）：
   循环节点 → 下游节点，必须带 `sourcePortID="loop-output"`（批处理是 `batch-output`）

spec 写法（edges 三元/四元组的第 3、4 位是 port / target_port）：
```python
"inner_edges": [
    ["<循环id>", "<首块id>", "loop-function-inline-output"],
    ["<首块id>", "<次块id>"],
    ["<末块id>", "<循环id>", None, "loop-function-inline-input"],
],
# 根层：
["<上游>", "<循环id>", None, "loop-function-inline-input"],   # 可选
["<循环id>", "<下游>", "loop-output", None],                  # 必须带
```

## 🔴 铁律 8：多分支汇合到一个「结束」必须用变量聚合（type 32）

一个结束节点的同名输入只能映射一个引用。答疑/教务/主调度这类「命中走 A、未命中走 B、
都要回 answer」的结构，必须在结束前加**变量聚合节点**：

```python
{"id": "100008", "type": "变量聚合节点", "title": "汇总回答",
 "merge_groups": [{"name": "Group1",
                   "variables": ["<命中分支>.answer", "<未命中分支>.answer"]}]}
# 结束节点引用 "100008.Group1"
```
变量聚合取组内**第一个非空值** —— 所以把「正常分支」放前面，
「固定话术/兜底」放后面；空串不算非空，不会盖住真回答。

## ⚪ 未配置态子工作流节点可以粘贴（E14 是预期 error）

子工作流节点 `workflowId` 留空串 = 画布上「添加了工作流节点但还没选」的原生状态，
**能粘贴**。校验器报 E14 属预期 —— 子工作流必须先建好并发布，父流才能在下拉里选到。
交付说明里写明「粘上后在节点下拉里选目标工作流」即可。
占位符（FILL_ME 开头）才会阻断粘贴，空串不会。
