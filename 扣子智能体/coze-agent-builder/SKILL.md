# coze-agent-builder

## 核心认知：流程型 ≠ 问答型

如果产品需求里出现「跟踪进度」「自动提醒」「按阶段推进」「记住用户状态」，那它就不是问答机器人，
不能靠堆提示词实现。真正的骨架是：

| 组件 | 角色 | 负责什么 |
|---|---|---|
| 知识库 | 参考书 | 通用方法论、长文档规则原文 |
| 数据库 | 记事本 | 状态、进度、跨会话记忆 |
| 工作流 | 手脚 | 确定性流程、多步操作、异常分支 |
| 系统提示词 | 人品 | 角色、流程路由、边界铁律 |

## 第一步：需求 → 四抽屉映射

Coze 只有四个地方能放东西：**插件 / 工作流 / 知识库 / 数据库**（外加系统提示词）。
逐条把需求对号入座，做成表格。对不上的要**明确指出来**，通常是两类：

1. **架构问题而非功能问题**（典型：「数据加密」——Coze 数据库明文存储、无字段级加密，
   正确做法是架构上不落敏感数据，不是开开关）
2. **平台没有该能力**（典型：「查重」——Coze 无官方查重，不要接来路不明的第三方接口，
   改做「查重前自检清单」）

## 第二步：数据层设计（必须先做，否则工作流里选不到资源）

### 职责切分（避免双份维护）

**判据：会因为"换一个对象"而变化的信息 → 数据库；换个对象也照样成立的信息 → 知识库。**

反例：把"需提交材料""格式规范"同时写进数据库表和知识库文档 → 改一处忘一处，
最终系统给出互相矛盾的说法。这类"因校/因公司而异"的信息只应放数据库。

### 完整落位判据（四类，带第四类）

| 信息性质 | 落哪 |
|---|---|
| 会在**不同个体**之间变化 | 数据库（业务数据） |
| 同一对象对所有个体都一样 | 数据库（规则数据） |
| 跨对象都成立、用于**生成回答**的参考知识 | 知识库 |
| **只是某个个体的凭证原件** | **附件存储，不参与检索** |

**第四类最容易被误放进知识库。** 典型：学生的毕业设计任务书、员工的劳动合同、
客户的合同扫描件。判断要点：

- **不能进知识库**，因为 ① 检索污染——个体文档彼此高度相似，A 提问会命中 B 的段落，
  得到"看起来对其实是他人的"答案；② 答非所问——知识库答"通常情况"，个体文档答"你这一次"；
  ③ 合规风险——含真实姓名/学号/证号，进检索库就可能被任何提问召回复述。
- **正确做法是"三拆"**：个性化字段 → 业务表；其中的统一规定部分 → 规则表；
  原件本体 → 附件，只提供"查看/下载"。
- 记忆版：**知识库是参考书，个体文档是作业本。参考书能共用，作业本只能本人看。**

### 表数怎么定：分三档，不要一步到位

| 档位 | 表数 | 判定标准 |
|---|---|---|
| 最小闭环 | 3 | 能建档、能引导、能记进度 |
| 验收完整 | 5 | + 记录类表（检查记录、拦截日志）→ 有可验收证据 |
| 上线可用 | 6~8 | + 驱动"自动提醒/催办/预警"的时间维度数据 |

**判断某张表是不是必需，问一句：没有它，哪个已承诺的功能做不出来？**

- 需要"自动推进/催办/预警" → 必须有**节点级**的时间表（阶段级的单个 `deadline` 字符串不够用，
  算不出"距下一节点还剩几天"）。典型表：`*_milestone`（含 `start_date` / `end_date` / 产出物）。
- 一个"阶段"下可能有多个"节点"（不同专业的节点划分还不一样）→ 加一个
  `mapped_stage` 字段把各对象的自定义节点**翻译**成统一阶段，主流程就不用为每个对象改。
- "实体"和"事件"要拆表：人的档案 / 事的档案分开，用 id 关联。合并后一旦换题、转岗、续约，
  历史就被覆盖，查不到"原来是什么"。
- **不要为可推导的数据建表**：如"推送去重"不需要 `push_log`，如果流水表已有
  `action` 字段，写一条 `action='推送'` 查最近一条即可。

### 让"替换进度"可量化：加 `data_source` 字段

规则表/业务表都建议加 `data_source`（枚举：`demo_template` / `official` / 其他来源标记）。
作用：**一眼看出哪些还是演示数据**，替换进度可查询（`GROUP BY data_source`），
不必靠记忆或另开文档跟踪。Demo 数据不要用"假对象名"伪装真实感，
**对象名用真实的、标注来源为模板**，比全用 XX/YY 更可用（可核实、可关联）。

### ★ 通用模式：把「承诺」落成「字段」（比 data_source 更值得记的一条）

设计表时对着需求文档逐条问：**这条承诺，系统靠什么保证它被执行？**

| 口头承诺（写在文档里） | 应落成的字段/默认值（写在数据里） |
|---|---|
| "标准答案必须人工抽检才能对外" | `review_status` 默认 `待审核`，**取题侧只允许读 `已通过`** |
| "评分只作教学参考，不作正式依据" | 字段名直接叫 **`ai_score`** 而不是 `score` —— 风险嵌进字段名，接手的人一眼看到 |
| "路由准确率要持续调优" | 一张 `route_log`（`routed_to` + `is_correct`），否则"调优"是句口号 |
| "资料替换进度要能跟踪" | `data_source` 枚举 + `GROUP BY` |

> **判据：凡是"承诺了但没人会去检查"的要求，都追问一句 —— 能不能变成一个字段／枚举／默认值？**
> 写在文档里的要求会被遗忘，写在字段里的要求会被系统执行。
> **方案负责承诺，数据层负责兑现。**
>
> 配套的一条：**"必须优化"这类话，如果没有一张表记录对错，就等于没说过。**
> 测试数据里**刻意留几条错误样本**（如 `is_correct=false` 的误判），能让这条链路一建好就有东西可演示。

### 真实数据的诚实边界（重要）

- **能核实的要用真实值**（如机构名称、标准号）。宁可花几分钟联网核对，
  也不要用占位名——尤其当名称可能已变更时（例：一批高职已升格为职业本科，沿用旧名即出错）。
- **核实不到的要如实标注"未查到"**，绝不用看起来合理的数字填坑。
  在数据里直接写 `⚠️ 公开文件中未见相关规定，须向 X 确认`。
  这既是数据诚实，也**恰好是产品里"宁可说不知道也不编"铁律在数据准备阶段的体现**。
- 演示模板要从**政策/类型差异**出发做差异化，而不是随机差异化。
  例：职业本科"一般不要求撰写毕业论文"是有政策依据的→决定了必须有 `*_type` 字段承载此差异。

### 三个必踩的坑

**坑 1：兜底数据永远查不到（最隐蔽）**
表里放了 `xxx='通用'` 的兜底行，但查询条件写死 `xxx = 用户值` → 逻辑上不可能匹配到兜底行。
- 正确：查询①精确 → IF **长度 == 0** → 查询②兜底 → 变量赋值标记来源
- 返回条数要 > 1（同一对象同一条件下可能有多条细分规则）

**坑 2：状态表用 Insert 会累积重复**
语义是"一个实体一条当前状态"的表，用 Insert 写入 → 用几次就存几条，查询无法判断最新。
- 改为**追加型流水表** `*_log`：写入永远 Insert，查询按时间倒序取第一条
- 附带好处：能看出变化轨迹（这是做周报/预警的数据基础）

**坑 3：时间字段用 String**
字符串排序会出错（`2025-1-9` 会排到 `2025-01-10` 后面），且算不了"还有几天"。
- 绝对时间一律 **Integer 时间戳（秒）**
- 相对表述（"第8周前"）才用 String
- **所有日期由时间插件提供，不要让大模型推算**（模型算日期十次错三次）

**例外（这条我写错过一次，已修正）**：要区分「发生时刻」与「计划日期」，但**不要用字符串解决**。
- **发生时刻**（`created_at`、`updated_at`）→ Integer 时间戳
- **计划日期**（任务书节点起止、合同起止、学期日程）→ **双字段**：
  `xxx_ts`（Integer 时间戳，**用来算**）+ `xxx_label`（String 文本，**用来看**）

⚠️ **曾经的错误做法**：认为"计划日期只需展示、只需与今天比较，所以用 `YYYY-MM-DD` 字符串更合适"。
**这个论证有致命漏洞** —— 一旦要算"距下一个节点还剩几天"，字符串就断了；
而这恰恰是里程碑/日程类表**存在的唯一理由**。此外各来源日期写法并不统一
（`2025-12-21` / `第11周` / `11月上旬`），纯字符串无法统一处理。
**宁可多写一个字段，不要赌它不需要计算。**

**坑 4：边界守卫的意图枚举漏类（漏一类 = 放行一类）**
守卫工作流用大模型做意图分类时，枚举必须把**每一类"该拦的请求"都列出来**。
漏掉一类，该类请求就会被判为正常而放行。
真实案例：`intent` 只列了「代写内容/编造数据/代做代码/代做PPT」，
**漏了「规避查重」和「规避AIGC检测」** → 学生说"帮我降重躲过查重"，系统判为正常指导。
**规避类必须与代写同级**——性质相同：都是让不达标的内容通过审查。
- 枚举（8 值）：正常指导 / 代写内容 / 编造数据 / 代做代码 / 代做PPT / **规避查重** / **规避AIGC检测** / 其它
- 判据是**目的**，不是措辞：学生把"去AI味"说成"帮我润色得自然点"，要按目的判。
  句中若出现「检测」「查重」「AI率」「查不出来」「降」等词 → 往规避方向判
- 拒绝话术要**分情况**：对规避类讲"结构骨架+反问"是答非所问，应给
  「一句话划界限 + 一句话法律依据 + 合规替代路径（本人重写 / 如实标注 / 主动报告导师）」

**坑 5：把「校规」当「国标」写进知识库**
字号字体、页边距、行距、查重阈值、AIGC 阈值——这些都**没有全国统一标准**，是各校自定。
真实对照：同样是"章标题"，荆楚理工学院=三号黑体居中、北师大=三号黑体、
四川大学=小3号标宋黑体、广东工业大学=三号黑体加粗、郑州工商=三号黑体3倍行距。
**后果**：写死一套数字进知识库 → 换所学校就答错，学生照做还会被格式检测扣分。
**正确切分**：
- 全国成立的（国标条文、法规、通行做法 + 判断原则）→ **知识库**
- 因校而异的（具体字号、页边距、阈值）→ **数据库 `school_rules.format_rule`**
- 系统话术：**"具体以你学校模板为准"**，绝不替学校说一个数字
- 判断原则（比记数字有用）：同一层级内字体一致、层级间字号递减、标题比正文醒目、全文不超过 3—4 个层级

**坑 6：AIGC 检测是 2025 年后新增的合规面**
- 《中华人民共和国学位法》**2025-01-01 施行**，第三十七条：学位论文或实践成果存在
  **代写、剽窃、伪造**的，**不授予学位或撤销学位** → 拦截代写从"校规级"升级为**法律级依据**。
- AIGC 检测已与查重并列成为送审前标准动作，**各校阈值不一**（20% / 35% / 40% 都有）。
- 知识库须覆盖：学位法、教育部令第 34 号/第 40 号、本科抽检办法、AI 使用允许/禁止范围、三项检测关系。
- **"帮学生降低 AIGC 率"与"帮学生降重"同质，都属规避审查，必须拦。**

**坑 7：可选参数进了 AND 精确匹配条件（静默失败）**
- 现象：开始节点把某入参标成"非必填"，查询节点却写 `字段 等于 {{该参数}}`，条件逻辑是 AND。
- 后果：用户不填 → 条件变成 `= ''` → **整条查询恒返回空**。不报错、不提示，
  只是**永远降级到兜底**——用户照样拿到一份"看起来正常"的通用回答，**没人会察觉它降级了**。
- **铁律**：查询条件里出现的每个值，都必须是"一定有值"的——**必填字段或固定值**。
  可选参数只有三种正确用法：
  ① 不参与查询，只做展示/校验；② 用「为空 / 不为空」单独做分支判断；
  ③ 用条件判断节点先分流，再走不同的查询条件。
- **常见变体**：拿精确匹配去比对用户手填的自由文本（"软件技术" vs
  "软件技术(企业应用软件方向)"），同样静默降级。应在主智能体侧要求"传入值与档案里的值完全一致"。
- **验收方法**：同一组输入跑两次，只让那个可选参数一填一空，**两次结果必须相同**。
  不同 = 它还在查询条件里。

**坑 8：回退链设计了 N 级，数据层却只有 1 级**
- 现象：工作流写了"专业级 → 学院级 → 学校级 → 类型兜底"四级回退，
  但表里只有专业级数据，**兜底行一行都没有**。回退逻辑写了等于没写，每级都查空。
- 更坏的是注释里往往写着"兜底数据是齐的，这个分支走不到"——**这句话通常是错的**，要实测。
- **自检口诀：回退链有几级，表里就要有几类行**
  （专业行 ／ `major='通用'` 行 ／ `school='通用'` 行）。
- **顺手对齐口径**：同一项目里若多张表都做了兜底，检查它们的兜底层级是否一致
  （典型翻车：规则表有 18 行兜底、进程表 0 行）。
- **层级越多越要警惕**：能合并的层级就合并（如"学院级通用"和"全校通用"内容雷同，
  且"用户没填学院"时学院级语义根本不成立）—— **回退链越短越不容易出错**。

### ★★ 平台硬约束（下面三条曾让整套方案作废，务必先看）

**坑 9：给一条工作流画了多个结束节点**
- 现象：一条工作流里按分支各画一个「结束」，例如 `结束(blocked)` + `结束(pass)`，
  或 `not_registered` / `need_more_info` / `advanced` 各一个。
- 官方原文：**"每个低代码工作流都默认包含一个开始节点和一个结束节点。"**
  **开始和结束都只有一个**——这不是建议，是硬约束。
- 为什么平台要这么设计：**工作流的输出定义写在结束节点上**。两个结束节点 = 两套输出定义，
  调用方（工作流节点）不知道该按哪套取输出，所以干脆不允许。
- **两种正确画法**（判据：**分支的产出会不会被结束节点或分支之后的节点引用？**）：
  - **画法 A：不会被引用 → 直接汇合**，连合流节点都不用加
    （一条分支做事、另一条什么都不做；或两条路都只是写库）
  - **画法 B：会被引用 → 用「变量聚合」**（两条分支产出的必须是"同类东西"）
- **连带效应**：结束节点**不能做计算**。所以"总数、汇总、拼接话术"这类东西
  **必须在结束节点之前用一个代码节点算好**。改成单结束节点后，往往会多出 1~2 个代码节点，
  **这是正常的，不是多此一举**。

**坑 10：用「变量赋值」节点做工作流内临时变量 / 分支合流 / 打标签**
- 现象：工作流画布上找不到、或加进来**选不出目标变量**，于是认为"Coze 没有这个节点"。
- 官方定义（在《变量》文档里，不在工作流文档里）：
  > "变量赋值节点：用于为变量 `name` 赋值，引用问答节点的输出参数。"
  > **"如果工作流中无变量，请先前往试运行，关联有变量配置的智能体后再选择变量。"**
- **第二句就是答案**：它操作的是**智能体变量**（在智能体编排页定义、跨会话持久化、
  最多 30 个、**只有 String 类型**），**不是工作流内的临时变量**。
  你不在智能体里定义变量，它就选不出目标 —— 现象上等于"没这个节点"。
- ⚠️ **更危险的用法**：拿智能体变量存"本次请求的判定结果"。官方说智能体变量**跨会话持久化**，
  **"测试后记得重置，否则会一直累加上去"**。
  于是：学生 A 被判违规写了 `blocked` → 学生 B 正常提问但这一步没写变量 → **变量还是 `blocked`**
  → **学生 B 被误拦，而且你从代码里完全看不出原因**（跨会话状态污染，排查成本极高）。
- **替代方案（三选一）**：
  | 想做的事 | 正确工具 |
  |---|---|
  | 算一个中间值给下游用 | **代码节点**（节点输出即变量） |
  | 在两条分支上打不同的标签 | **分支之前的代码节点**一次算完（分支条件在那个节点里已知） |
  | 把两条分支的结果合成一个 | **变量聚合节点**（官方就是干这个的） |
  | 记"当前阶段"这类跨会话状态 | **数据库表**（本来就该在数据库里） |

**坑 11：把"状态判定"放在分支里，导致静默失效**
- 现象：合规守卫节点要返回 `pass` / `blocked`，写法是"违规分支上放个赋值节点写 `blocked`，
  正常分支上放另一个写 `pass`"。**结果工作流照跑、`out_status` 是空值**，
  主智能体拿到空值大概率**当成"没拦截"放行**——**这道门是虚掩的**。
- **根因**：以为状态是"分支走出来的结果"，其实**它是分支条件的另一个名字**。
- **正确解法：把状态判定提到分支之前**。判断"是否违规"的那个分类节点/代码节点，
  顺手把 `status` 一起输出：
  ```python
  # 分类节点产出 status，它在分支之前 → 两条路径上都有值
  {"intent": "...", "is_violation": True, "status": "blocked", "action": "已拦截"}
  ```
  结束节点直接写 `out_status = {{意图分类.v_status}}`，
  **既不需要赋值节点，也不需要变量聚合**。
- **可复用规则（两类状态别混）**：
  | 类别 | 特征 | 处理 |
  |---|---|---|
  | **校验类**：`pass` / `blocked` / `not_registered` / `need_more_info` | "看一眼数据就能定" | **分支之前**算，结束节点无条件引用 |
  | **结果类**：`advanced` / `checked` / `created` / `failed` | "做完了才算数" | **分支之后**定，用固定值 + 变量聚合 |
  ⚠️ 把结果类当校验类 → **假成功**（状态说改完了、数据库其实没动）。

**顺带三条纪律**：
- **分支用来分流"做不同的事"，不用来分流"说不同的话"**。
  语气差异（宽裕版/催办版）应该让代码节点算个标记（如 `v_urgent = normal|soon|overdue`），
  交给**同一个**提示词按规则选语气 —— 少一个节点、少一份维护、**结果可测**。
- **能在分支之前算的，绝不放到分支之后**。分支前的节点在**所有路径**上都执行，
  它的输出可以被下游**无条件引用**，**省掉整套变量聚合**。
  实战里一个代码节点取代 4 个节点是常事。
- **代码节点的每个 `return` 都要写全所有输出键**。输出结构是"契约"，
  少一个键 → 走到那条路径时才报"变量不存在"，**极难排查**。

**「变量聚合」节点的官方行为（三句话就是操作要点）**：
> - "能够将**多路分支的输出变量整合为一个**。"
> - "如果**有任意一个分支未运行**，汇总输出的节点会从该分支读取到一个**空值，从而导致工作流运行报错**。"
> - "变量聚合节点会读取多路分支中**第一个不为空的值**。"
> - "支持**分组聚合**，每组变量会聚合为一个输出变量，**分组组内的数据类型必须相同**。"
>   输出变量固定为 `Group1`，多分组递增 `Group2`、`Group3`。

① 取第一个非空值 → **主分支排前面**；
② 未运行分支读到空值 → **下游必须经聚合引用，不能直接引用分支内部变量**；
③ 组内类型必须相同 → **String 和 Object 要开两个分组**。

### 读用户给的文档（.docx 常是关键信息来源）

用户提供的原始文档往往是真实规则的最佳来源（比让你编的模板可靠得多）。本机可能没有
`python-docx`，**零依赖提取法**：`.docx` 就是个 zip，解 `word/document.xml` 即可。

```python
import zipfile
from xml.etree import ElementTree as ET
W = "{http://schemas.openxmlformats.org/wordprocessingml/2006/main}"
def para_text(p): return "".join(t.text or "" for t in p.iter(W + "t"))
with zipfile.ZipFile(path) as z:
    body = ET.fromstring(z.read("word/document.xml")).find(W + "body")
for child in body:                     # 必须遍历 w:p 和 w:tbl 两种
    if child.tag == W + "p":   print(para_text(child))
    elif child.tag == W + "tbl":        # ← 千万别漏表格
        for tr in child.findall(W + "tr"):
            print(" | ".join(" ".join(para_text(p) for p in tc.findall(W + "p"))
                             for tc in tr.findall(W + "tc")))
```

**关键提醒**：这类文档的核心信息（时间节点、清单、评分项）**几乎全在表格里**。
只提取 `w:p` 会丢掉最有价值的部分。读到原文后，再用上面的落位判据拆到对应表/知识库。

### Coze 建表注意事项

- **不要手建 `id` 字段**，平台自动生成主键，手建会冲突
- 平台类型只有：文本 / 整数 / 浮点数 / 布尔 / 时间
- **查询结果永远是 `Array<Object>`**，哪怕设了返回 1 条。取值必须写 `{{节点.字段}}[0]`
- **判空用"长度 == 0"**，不要用字符串判空（数组类型用字符串判空永远不成立）
- 平台**不提供 SQL 输入框**。要生成表时，产出「给 Coze AI 的自然语言建表指令」让它自动建，
  SQL 只作为表结构说明书和本地验证用
- 数据导入优先用 **CSV/Excel**（比手敲快）；CSV 用 **UTF-8 无 BOM**，否则首列字段名会带隐藏字符
  - ⚠️ **无 BOM 的 UTF-8 在 Excel 里双击打开会乱码** —— 这是「导入要无 BOM」与「人要看」的冲突。
    解法是**双份交付**：`*.csv`（UTF-8 无 BOM）给 Coze 导入，另出一份多 sheet 的 `*.xlsx` 给人核对。
    交 CSV 时**必须告诉用户"别双击打开，会乱码"**，否则他第一反应就是"你数据生成错了"。
- **查询操作符辨析（极易望文生义用错）**：查询数据节点支持
  等于(=)、不等于(!=)、**模糊匹配(LIKE)**、**包含(IN)**、为空(IS NULL)、不为空(IS NOT NULL)。
  - **`包含` 是集合操作 `IN (值1, 值2)`，不是字符串包含。**
  - 字符串包含要用 **「模糊匹配」**，且后端**自动在值前后补 `%`**，**不要手写 `%`**。
  - 「模糊匹配」传空值时会变成 `%`（匹配所有行），理论上可当"忽略该条件"用；
    但**有第三方实测反馈它出现过匹配不上的情况**，且失败是静默的——
    **别把核心逻辑建在它上面**，只作可选增强（失效仅降级，不破坏主逻辑）。
  - 要判断"用户有没有填"时，直接用**「为空 / 不为空」**操作符或条件判断节点，更确定。

## 第三步：工作流逐节点配置模板

每个节点必须写清这 6 项，缺一项就不可执行：

```
节点类型 / 前驱节点 / 后继节点
输入变量（变量名 + 类型 + 来源）
配置（节点内部怎么填）
输出变量（变量名 + 类型）
```

**变量命名前缀**：`in_`(入参) `q_`(查询结果) `k_`(知识库) `llm_`(大模型) `v_`(中间变量) `out_`(输出)

**用 `out_status` 做统一接口契约**。给每个工作流定义返回状态（`pass` / `blocked` / `created` /
`need_more_info` / `not_registered` / `checked` / `parse_failed` / `started` / `failed`），
智能体提示词就只需要写"根据 out_status 决定下一步"，不必为每条工作流写一段说明。

**分流后一定要合流**：两条分支（如精确查询/兜底查询）各自的结果赋值到**同一个变量**，
下游节点只引用这一处。否则下游要为每个分支写一遍，分支数量指数爆炸。
⚠️ 合流要建**多个赋值节点**（每条分支一个），目标变量名必须完全一致——单个赋值节点接多条入线是取不到值的。

**跨工作流同名变量必须同名**。同一个含义在不同工作流用不同名字，后期维护会失控。

### 三个可复用的"标准零件"（几乎每个项目都要）

| 零件 | 适用场景 | 实现要点 |
|---|---|---|
| **两步查询** | 有"兜底/默认"数据 | 查①精确（带对象名）→ 判**长度==0** → 查②兜底（`对象='通用' AND 分类=当前分类`）→ 合流 |
| **多级回退** | 粒度细的数据（如"某专业的排期表"） | 精确 → 上级通用 → 全局通用 → 按分类兜底 → 全部落空时**明确说不知道**，不编造 |
| **时间计算** | 算"还剩几天/是否逾期" | 入口传 `now_ts`（**整条流程只用一个时间**）→ **代码节点**算，禁止大模型 |

⚠️ **兜底查询必须带上"分类字段"**。只查 `'通用'` 会把不同分类的兜底数据一次捞出来混在一起
（例：把"本科"的要求给到"职业本科"）。**兜底数据本身就要按分类分组存。**

⚠️ **复用 ≥3 次的逻辑要独立成一条子工作流**（平台支持"工作流节点"嵌套调用）。
内联意味着"改一处要改四处"，而这类回退查询偏偏最需要反复调整。
代价：**它必须先发布**，否则调用方在画布上选不到它。

### 时间/数值计算一律用代码节点，不要用大模型

日期减法是纯数值运算，代码 **100% 准确、零成本、毫秒级**；大模型既慢又错。
验收标准是**"同一输入跑两次，结果完全一致"**——不一致就说明用了大模型算。
（Coze 代码节点支持 Python，`async def main(args: Args) -> Output`，直接粘贴即可。）

## 第四步：先建边界守卫工作流

如果产品有"不代做 / 不越界 / 合规"要求，**第一条就建守卫**——它定义行为边界，
边界没定后面全部可能返工。而且它通常最简单，半天能做完。

**必须双保险**：
- 提示词铁律（第一道门）——写在系统提示词最前面，标注最高优先级
- 工作流拦截（第二道门）——意图分类 → IF → 拒绝话术改写

⚠️ **守卫是"坑 11"最容易翻车的地方**：`pass` / `blocked` **必须由那个意图分类节点在分支之前就输出**
（`is_violation` 和 `status` 一次给全），结束节点直接引用 `{{意图分类.status}}`。
**不要**在两条分支上各放一个赋值节点去写状态——那需要两个结束节点（不合法），
而且失败时是**静默的**（`out_status` 为空，主智能体大概率当成没拦截放行，**这道门就成了虚掩的**）。

**两个容易被忽略的设计点**：
- 两条分支**都要写日志**（正常 + 违规），否则算不出拦截率，也没有迭代数据
- 拦截分支的返回要**直接输出、禁止智能体自行改写**，否则会被绕过
- **防误伤测试比拦截测试更重要**（"这段代码为什么报错"必须放行），守卫太激进会让产品不可用。
  判定原则写进提示词：**宁可漏判，不要误伤**
- **关键词兜底节点要放在「被判为正常」的那条路径上，不要放在意图分类之前**
  （2026-09 实测补）。放前面 = 用概率性的词表**覆盖** LLM 更准的判断，误伤成倍上升；
  放正常路径上 = 只补漏。接法：意图识别的 `branch_0`（正常）+ `default`（未匹配）
  两者都扇入这个复核节点，命中关键词才拦，否则放行。
  ⚠️ 代码节点里**放行词表的判断必须排在拦截词表之前**，反过来会误伤一大片
  （"帮我改一下我写的作文"会先命中「帮我」+「写」）。
- **关键词匹配用「请求词 × 动作词」双命中，不用单关键词**：
  `'帮我写' in q` 这种单串匹配漏得厉害（"帮我把这篇翻译做完"就不匹配）。
  具体写法与本地实测方法见 `coze-node-authoring` 的 `references/06-code-node-python.md` 末节。

**拒绝话术要按违规类别分叉，不能一套打天下**（V3 教训）：
"要求代写内容"和"要求规避检测"是两类完全不同的诉求——
前者想要**内容**，后者想要**绕过审查**。用"给你个框架 + 反问你几个问题"去回答
"怎么让检测查不出来"，属于答非所问。
- 代做类 → 四段式：表明立场 + 结构骨架 + 反问 + 后续可检查项
- 规避类 → 三段式：划界限 + **一句法律依据** + **合规替代路径**（这是重点，要具体可执行）
判据是**目的而非措辞**："帮我润色"（目的是更好）→ 放行；"帮我改得不像 AI 写的"（目的是躲检测）→ 拦截。
伪装性最强的请求往往长得像正常请求，**必须在提示词里明确写"出现『检测/查重/AI率/降』等词就往规避方向判"**。

⚠️ **日志表的"指标分母"不能被污染**（V3 教训）：
如果产品要用某张表算比率（如"拦截率 = 违规数 / 总提问数"），
**任何非该语义的记录都不能写进去**。
反例：把"模拟答辩"的评分记录写进问答日志表 → 每做一次模拟，分母就变大、比率被稀释，
**而这恰恰是要交付给客户的核心指标**。判据：**写进这张表前先问"这条记录在语义上属于这张表吗"**。

**多 Agent 模式下边界约束不继承**，每个子 Agent 都要单独重写铁律。

### 多 Agent 画布的三类节点 + 四个易错点（依据：`coze.cn/docs/guides/multiagent` 官方原文）

| 节点类型 | 能力 | 怎么用 |
|---|---|---|
| **Agent 节点**（画布内新建） | 官方：「**技能**：单击 `+` 添加 Agent 所需使用的**工具、工作流或知识库**」<br>只活在当前画布，不可被别的画布引用 | 一段提示词就够的子任务：兜底、澄清、边界引导、格式转换 |
| **智能体节点**（引用**已发布的单 Agent** Bot） | 独立智能体，可"查看和更新智能体配置"，有自己的全局配置层 | 需要独立发布 / 独立迭代 / 独立验收的专项助手 |
| **全局跳转条件** | 硬触发关键词直达，**单 Bot 上限 5 条，优先级高于「适用场景」** | 漏一次就是事故的拦截（如代写） |

> ⚠️ 网上有教程称「Agent 节点挂不了工作流」—— **与官方文档冲突，以官方为准**。
> 但**建的时候点一下 `+` 亲眼确认**，别把"文档说可以"当成"已验证"。

**四个易错点（每一个都踩过）**：

⇒ **① 左侧「人设与回复逻辑」≠ 某个 Agent 的提示词。** 官方：「该区域中的配置是**全局配置，将适用于所有添加的 Agent**」。
主管自己的调度提示词在**画布根节点卡片的「Agent 提示词」**里 —— **两个位置都要填，内容不同**。
（左侧最适合放身份/语气/红线：声明一次，画布内所有节点继承。）

⇒ **② 平台字段名是「适用场景」，不是"描述"。** 官方：「说明此节点的功能和适用场景，
**用于帮助前序节点判断在何种情况下应该切换到此节点**」。所以它是路由第一变量。
一段合格的适用场景 = 适用情形 + 3~5 个带用户原话的问法示例 + **「不适用」边界（点名相邻节点）**。
第三条最关键 —— **路由错误绝大多数不是"选错"，是"两个节点都像"。**

⇒ **③ 开始节点分发策略要选「开始节点」，不要选「上一次回复用户的节点」。**
后者会把用户**困在同一个节点里出不来**：独立子 Bot 自己**没有转交能力**（转交属于画布）。
反例：用户问完"请假提前多久"（教务）后说"顺便看看我这篇作文" → 消息仍发给教务节点 → 答不了、卡死。
选「开始节点」则每条消息重判一次，换话题能自然切换。

⇒ **④ ⚠️ 本节 v1 曾写「表数 > 3 就必须拆 Bot」，该结论已推翻，保留痕迹别再犯。**
>
> | v1 说的 | 实际 | 错因 |
> |---|---|---|
> | 「数据表创建在智能体编排页面，**属于该智能体，不是工作空间级资源**」 | 数据库**有两个创建位置**：**资源库**（工作空间级）+ 应用（智能体）内 | 只看了一个入口就下全称判断 |
> | 「单 Bot ≤ 3 张表，表数超过 3 就必须拆 Bot」 | "3 张"限制的是**智能体层绑定**，**很可能不适用于工作流层** | 上一条推论跟着错 |
>
> **三条官方原文**（合起来才完整）：
> - 《创建扣子数据库》：「在左侧导航栏中单击**资源库** → 右上角 **+资源 > 数据库**」⇒ **可建在工作空间级**
> - `database_faq`：「在**低代码智能体**中添加数据库时，最多可添加 **3 个数据表**」⇒ 主语是**智能体**
> - `database_overview`：「低代码**工作流数据库节点**，每个节点最多可添加 **1 个数据表**」⇒ 限制的是**单节点**，对节点数无限制
>
> ⇒ **正确做法：表建在「资源库」，工作流用数据库节点操作（一个节点 1 张表，需几张放几个节点）。**
> ⚠️ **确定性：强推断，非直接原文** —— 官方没明写"工作流节点可选资源库任意表"。
> **建表后必做 1 次验证**：拖一个数据库节点 → 看下拉能否选到资源库里的表（1 分钟）。
>
> ⇒ **判据（通用的）**：**看到一条平台限制，先问"它限制的是哪个层、哪个对象"。**
> 限制条款都有主语，**主语错了整条推论就错** —— 这次直接导致"必须拆 Bot"的错误架构结论。

⇒ **那到底什么时候必须拆 Bot？** 三条真理由（都不是表数）：
1. 某个子模块要**独立发布**到单独渠道（飞书 / 微信 / 单独 API）
2. 某个子模块要**独立迭代、独立验收**（不同维护人、不同上线节奏）
3. 官方复杂度信号线：单 Agent Prompt **> 3000 字** ｜ 挂载 **> 5 个复杂工作流** ｜ 调试明显变难

⇒ **不是瓶颈的两项（被问到时要能直接回）**：知识库「单智能体**最多绑定 150 个**」；
工作流「在扣子智能体中**无工作流数量限制**」。

⇒ **多 Agent 模式下边界约束不继承**：官方说左侧全局配置适用于"所有添加的 Agent"，
但**引用的已发布 Bot 是独立智能体、有自己的一层全局配置**，父级大概率不覆盖它。
**红线内容宁可在每个子 Bot 里重复写一遍，也不要靠一个不确定的"继承"来守底线。**

⇒ **建多 Agent 的顺序坑**：被引用的子 Bot **必须已发布**，否则画布下拉里是空的。
先建子 Bot 最小版本（名字 + 功能介绍）发布掉，主 Bot 才有东西可引用。

⇒ **全局跳转条件是硬触发 —— 命中即跳，AI 没有纠错机会。** 关键词写宽了误伤（"帮我改简历"被拖去批改），
写窄了形同虚设。**判据：只有"漏一次就是事故"的请求才配用硬触发**，
其余交给语义路由 —— 后者判错了下一句话还能纠正，前者不能。**别把 5 条额度一次性用满。**

⇒ **主 Agent 不要挂知识库、不要挂联网插件。** 挂了两个副作用：
① 它会倾向自己抢答、绕过专项助手；② 手上握全部库，问教务可能召回教材 —— **分库隔离直接失效**。
**RAG 只发生在子 Bot 内部，主 Bot 保持"手里没资料"。**

### ★ 要不要上多 Agent？—— 选型判据（官方实践原文 + 踩坑实测）

**先默认单 Agent。** 官方实践原文：「**优先用单 Agent 自主规划**：能满足需求就不用上多智能体，
**降低开发复杂度**」；「**不要一开始就过度设计**，先从单智能体做起，复杂度上来后再逐步拆分子 Agent」。
**官方给的拆分信号线**：单 Agent Prompt **> 3000 字** ｜ 挂载 **> 5 个复杂工作流** ｜ 调试排障明显变难。

**⚠️ v1 曾写「需要统一入口时只能靠多 Agent」—— 错，已更正。**
**单 Agent 本身就是统一入口**：所有问题都发给它，它在**工作流内**分流到各子工作流。
「统一入口」≠「分发到不同 Bot」。Coze 工作流确实**没有"调用 Bot"的节点**
（能调的只有插件/子工作流/大模型/代码/知识库检索/数据库/意图识别/选择器/循环批处理），
但**这不妨碍单 Agent 做入口** —— 因为分流后走的是**子工作流**，不是另一个 Bot。

⇒ **多 Agent 真正不可替代的只有一种情况**：子模块需要**独立发布 / 独立迭代 / 独立验收**。
若只是"要一个入口接住所有问题"，**单 Agent + 1 条主调度工作流**就够，而且更简单。

**★ 推荐形态：单 Agent + 1 条「主调度工作流」（不是挂 N 条让 LLM 自己选）**

| 方式 | 机制 | 问题 |
|---|---|---|
| Agent 挂 N 条工作流，LLM 按描述选 | 「大模型会根据工作流描述自动选择调用哪一个」 | 工具越多越不准；官方信号线 **> 5 个复杂工作流**就该拆 |
| ✅ **Agent 只挂 1 条主调度工作流** | 工作流内：**意图识别节点 + 选择器**分流 → 调子工作流 | 无 |

```
用户 → 单 Agent（身份/语气/铁律 + 硬指令"所有请求先走 WF-00"）
       → WF-00 主调度工作流
          ① 调 WF-01 守卫（子工作流）← 守卫排在路由之前 ✅
          ② 选择器：被拦？→ 直接结束输出引导话术
          ③ 意图识别（N 类 + 兜底）
          ④ 选择器分流 → 各子工作流 / 兜底话术
```
⇒ **这个形态比多 Agent 更好**：守卫能排在路由**之前**且是工作流（有结构化输出、可写日志、可实测）；
路由是确定性分支，不是概率性工具选择。**多 Agent 的主 Agent 挂不了工作流**
（2026-09-25 实测），所以它反而做不到这一点。

**⚠️ 最容易被误解的一点：「IF 分流」和多 Agent 路由不是替代关系，而是两层。**

| | 多 Agent 路由 | 工作流 IF 分流 |
|---|---|---|
| 分流发生在 | **Bot 层**（1 次） | **工作流层**（多条） |
| 机制 | LLM 黑盒语义匹配 | 显式分支（意图识别 / 选择器） |
| 可控性 | 不可控，**必须实测调优** | 看得见、测得准、改得动 |
| 调试 | 需看完整调用链日志 | 节点少，容易定位 |

⇒ **正确姿势是两层各管一段**（v1 说"两者叠加"也对，但主次说反了）：
**分流主力在工作流层**（确定性、可测、守卫能前置），**Bot 层只在"要独立发布"时才拆**。
把"交给不同 Bot"当成默认目标，会白付多 Bot 的维护成本。

**感知到的"麻烦"要拆开看 —— 大半是自己加出来的：**

| 复杂度来源 | 必须付？ | 处理 |
|---|---|---|
| 多 Agent 编排本身 | ❌ **非必须** | v1 说"由表数上限 + 统一入口逼出"**两条理由都不成立**（见 ④ 与"统一入口"两节）。只在子模块需**独立发布/迭代/验收**时才付 |
| 子 Bot 先建后发布 | ✅ | 顺序坑，但**只痛一次** |
| 主 Agent 路由要实测调优 | ✅ | LLM 语义匹配的固有代价，靠"适用场景"质量 + 日志调优 |
| 数据表拆到 4~5 个 Bot | ❌ | **只为装表的话 2 个 Bot（3+3）就够**；拆到 4~5 个是"各助手独立维护"的业务需要，不是技术必须 |
| 全局跳转条件开满 5 条 | ❌ | 代写/越界拦截**放工作流里做**，比硬触发可控（硬触发命中即跳、AI 无纠错机会） |
| 加一个内嵌 Agent 节点做兜底 | ❌ | 兜底与澄清**合并进主 Agent 提示词**，省一个节点 |
| 红线在每个子 Bot 重复写 | ⚠️ 待验证 | 若左侧全局配置真能继承到已发布子 Bot，则只写 1 处；**不确定就先重复写**（重复只费 token，漏了是事故） |

⇒ **最小形态 =「一层路由 + N 个 Bot 节点」**，其余全部砍掉。
**如果有人反馈"多 Agent 太麻烦"，先问他是不是加了全局跳转条件、内嵌兜底节点、重复铁律 —— 这三样砍掉后并不麻烦。**

> 💡 文档写错平台机制时，**改文档要留"更正痕迹"**（第几版说了什么、错在哪、依据是什么）。
> 不留痕的话，下一个看文档的人会再踩一次同一个坑。

## 交付物清单（用户通常全都需要）

1. **总体方案**：需求→组件映射表 + 架构图 + 分阶段排期 + 避坑清单
2. **数据库建表包**：给 Coze AI 的自然语言建表指令 + SQL（本地验证用）+ 类型对照表
3. **可导入的数据文件**：CSV（UTF-8 无 BOM）+ Excel 汇总（多 sheet，方便核对与导入）
4. **知识库文档**：按一级标题分层，导入时选「按标题分段」。
   建议**同源生成三形态**（一条源头数据 → 三个产物）：
   `源文件/*.md`（改内容用）+ `导入_txt/*.txt`（导入 Coze，UTF-8 无 BOM）+ `导入_docx/*.docx`（**给客户看/演示用**）。
   ⚠️ **不要把 docx 传进知识库**（复杂表格解析会变形）；docx 的价值是让客户看到"我们整理了这么厚的资料"。
   ⚠️ **md 是否支持说法不一致**（官方 docs 只列 txt/pdf/doc/docx）→ **导入一律用 txt 最稳**。
   做法：内容源写进 Python 脚本（`_src_kbN.py` 的数据结构）→ 跑生成器批量产出三种形态，
   **不要单独手改 txt/docx**，否则下次重跑被覆盖。
5. **工作流逐节点配置手册**：按上述模板逐节点写，节点少可一份，超过 4 条工作流建议拆上下篇
6. **Demo 全流程手册**：按天排计划 + 每天的验证清单 + demo→真实数据切换方案
7. **验收清单**：功能项 + 边界项 + 数据项，逐项可勾选
   **另必须附一份"平台约束自查清单"**（一票否决项放在最前面）：
   ① 每条工作流只有 1 个结束节点；② 全篇没有「变量赋值」节点；
   ③ 要分流"不同话术"的地方没建分支；④ 结束节点引用的变量在所有路径上都有值；
   ⑤ 变量聚合的组内类型一致、主分支在前。
8. **每个构件的「归属契约」**（⚠️ 最容易被漏掉的一项）：
   交付一条工作流 / 一张表 / 一个知识库时，光给"文件在哪、怎么粘"不算交付完 ——
   必须同时写清四项元信息：

   | 要素 | 说明 | 例（WF-01 边界守卫） |
   |---|---|---|
   | **Owner（归属）** | 谁维护、谁看它的指标 | `01_主调度智能体` —— 谁看拦截率 |
   | **创建位置** | 建在资源库还是某个 Bot 内 | 资源库（工作空间级） |
   | **运行时触发点** | 从哪挂载、在哪一刻执行 | 主 Agent 根节点「技能→工作流」，**必须在路由之前** |
   | **依赖 / 待验证** | 它成立的前提 | 依赖 A-07 需求确认；"主 Agent 能否挂工作流"待实测 |

   ⇒ **归属 ≠ 挂载。** 归属决定"出问题找谁"，挂载决定"从哪触发"，两者可以不同
   （工作流归 A 的 Owner、被 A 和 B 共同挂载是正常的）。
   ⇒ **构建件的挂载点要选在"它该起作用的那一刻"。** 守卫类必须挂在**路由上游**，
   挂在下游会漏掉"路由判错就绕过"的情况 —— 等于把"能不能拦住"交给最不可靠的环节。
   ⇒ 判据：**交付一个构件，要交付到"接手人能独立行动"为止**，不是"文件给出去"为止。
   文件是"东西"，归属契约是"这个东西在系统里的位置"。

### 测试数据设计原则

三条，按优先级：

1. **对象名尽量用真实值**（真实机构名、真实标准号）。全用 `XX公司` / `YY学院` 的"测试数据"
   既无法核实也无法关联，用户几乎一定会问"能不能用真的"。核实用不了几分钟。
2. **用 `data_source` 字段标记来源**（`demo_template` / `official`），而不是靠命名前缀区分。
   好处：替换进度可 `GROUP BY` 量化查询；且真实数据与模板数据可共存一张表、逐步替换。
3. **数值/时间要满足基本可计算性**：时间戳要落在真实区间（用 `date` 命令取当前时间算偏移，
   不要自己推），进度节点要有起止日期，否则"还剩几天""催办"这类功能根本测不了。
4. 五张表**都要有量**，不能只有主表有数据、其余表各来 2 行——记录类表没量，
   验收时就演示不出"拦截 N 次""检查 M 份"。

**切换真实数据的第一步永远是备份**；切换后必查三项：有无真实证号入表、
有无原文全文入库、日志表有无混入个人信息。

## 其他关键坑

- **工作流改了必须重新发布**，否则智能体仍用旧版（改了没生效十有八九是这个）
- **子工作流必须先发布**，否则调用方在画布上选不到它（和"资源不存在就选不到"同一条规则）
- **工作流建在「资源库」（工作空间级），不要建在某个 Bot 内部**。两个理由：
  ① 被多个 Bot 共用的（"未命中转存"被答疑与客服共用、"运营统计"跨全 Bot）建在 Bot 内**引用起来别扭**；
  ② 半年后没人记得这条工作流当初是为哪个 Bot 建的。
  建在资源库 → 再按需挂到各 Bot 的「技能 → 工作流」。
- **工作流里做 RAG 检索时，query 必须写死为业务关键词，不能用用户原始输入。**
  学生问「我这篇作文能打几分」，拿这句话去检索「评分标准」**必然落空** ——
  query 要写成 `雅思写作 Task 2 评分标准 四项维度 分数档`。
  和"表格库索引列"是同一条底层原理：**检索方与索引方的用词必须对齐，靠设计，不靠运气。**
- **★ 多模态（图片）输入有两个必改项**（依据：官方 FAQ）：
  开始节点可设 `Image` 类型参数**直接接用户上传的图片**；
  但**大模型节点引用该参数时，「数据类型」必须手动设为 `Image`** ——
  官方把这条专门单列出来，说明**默认值是不对的**，不改就读不到图。
  若改用 URL 传参：**图片必须是公网可访问地址**；且**视觉理解模型不支持直接读 String 类型的图片 URL**。
  ⚠️ 别把"对话里发图片能识别"直接等价成"工作流里也能识别" —— 这是两条不同的链路。
- **★ 工作流失败时的对外话术，绝不写「服务繁忙，请稍后再试」。**
  这句话把故障变成**不可观测** —— 出题失败最常见的原因是**格式校验没过**（大模型没按 JSON 输出），不是"忙"。
  正确做法：校验失败 → **自动重试 1 次**（带上"上次格式不合格"的提示）→ 仍失败走**降级分支**并**写日志**；
  只有确实跑不出来才对用户说「这次没能生成符合规范的题目，已记录，建议联系教研老师」。
  ⇒ 配套要求：**生成类工作流的代码节点必须做「解析 + 校验 + 给布尔结论」三件事**，
  只解析不校验 = 把错误往后推，最后变成结束节点上的一句报错。
  校验结论交给**选择器**决定「入库 / 重试 / 降级」——**重试分支不能省**。
- **被 ≥3 条工作流依赖的子工作流，要排在主流程之前建**。它不同，调用方会**静默降级**——
  不报错，只是悄悄少一块数据（没有剩余天数、没有下一节点）。**这类问题最难排查。**
- **状态字段必须有专门的更新入口**。如果"当前阶段"只在建档时写一次，
  用户推进到下一阶段后系统还会一直按旧阶段给建议——**这是"陪着走完全流程"这类产品定位的致命伤**。
  要有一条独立的小工作流处理状态迁移，并记录"旧值→新值"（**能发现进度倒退，那是最强的求助信号**）。
- **枚举值必须跨文档统一**（连"其他 vs 其它"和值的顺序都要一致）。
  枚举是数据库的匹配键，写错一个字就永远查不到数据，而且**不会报错**。
  文档一多，最容易出现"A 文档写 6 个值、B 文档写 8 个值"这种断裂——交付前必须全局 grep 一遍。
- **知识库分段必须选「按标题分段」**，自动分段会把相邻章节的内容切到一起，检索必错
- **知识库平台硬限制（官方数字，规划前先倒推）**：单库 ≤ **300 个文件**；单文件 ≤ 100MB
  （**txt 与纯文本 Markdown ≤ 5MB**）；分段总数 ≤ **10000**；单分段 ≤ **5000 字符**；
  容量：免费版 **1GB** / 个人进阶版 10GB / 企业标准版 **100GB** / 企业旗舰版 2TB。
  → **另：内置数据库 ≤ 3 表/Bot、≤ 20 字段/表** —— 这两个数字是"为什么要加业务平台"最有说服力的论据，
  对外讲架构时直接抛出来，比讲道理有效十倍。
- **召回参数默认值**：搜索策略=混合 / TopK=**5** / 最小匹配度=**0.5** / 查询改写=**开** / 结果重排=**关**。
  调参判据：**答疑要「广」（漏召回会答不上）、出题要「准」（误召回会出错题）**
  → 答疑阈值低（0.55）、出题阈值高（0.60）；高度口语化的提问场景（客服）**必须开查询改写 + 结果重排**。
  阈值不能凭感觉定，**上线后必须用测试题实测再调**。
- **分库判据是「按回答依据的类型分」，不是「按 Bot 分」**：资料性质（更新快慢）/ 污染风险 / 召回参数 / 维护人，
  四项中任一项不同就该分库。同一份资料被两个 Bot 共用是**正常的**（教材库同时供答疑与出题），
  不要为了"一 Bot 一库"把它拆成两份、还得同步维护。
- **知识库必须配一张台账表**（`kb_material`：资料名 / 类型 / 版本 / 文件数 / 状态 / 责任人 / 索引路径 / 更新时间 / 备注），
  否则"支持知识库更新迭代"就是空话 —— 客户几百份资料，靠什么记住哪份已入库、什么版本、谁负责改？
  台账要与实际文件**一一对应**，状态含「待入库 / 已入库 / 已下架」，
  **替换资料时保留下架历史行**（审计追溯的基础），并**指定单一维护人**（平台不支持多人协作编辑知识库）。
- **表格知识库（≠ 文本库）**：`.csv`/`.xlsx` 导入，**默认按行分片**（一行=一片段）。
  典型用途：出题 Bot 的「章节知识点索引表」、客服的「班型价格表」、批改的「评分档位表」。
  - **容量规则是「一库一结构、可放 N 个同结构文件」**（限制页原文：单库最多 300 个文件；
    创建页原文：所添加表格结构须与库定义**完全一致**）。
    ⚠️ 别把这两句读成「一库只能一个文件」，也别读成「一张库什么表都能塞」。
    列数不同的表 = 必须分开建库。**不支持跨表 JOIN**（每表一库，物理上无法）。
  - **索引列是这张表能不能被搜到的开关**，且**只有一列**。官方原文：
    「指定**某一列**作为查询匹配的语义字段……将用户查询内容与**该列**内容对比」。
    ⇒ **索引列的值必须是「用户会说出来的话」**，不能是任何原始业务列
    （示例反例：索引列设成 `分数档`，值 `6.0-6.5`；学生问「我这篇能打几分」——
    这句话里根本没有那个值，必然匹配落空）。
    ⇒ **做法：表末统一加一列「检索关键词」作唯一索引列**，把「这一行会被怎么问」预先写进去
    （`判断题解题法 FALSE与NOT GIVEN区分 是非题`）。控制在 **2~5 个词**，拼长了会稀释语义。
    这列同时是**问法覆盖率自检表**；xlsx 里标底色提醒维护者别当普通列改。
  - **导入第 2 步「表结构配置」要逐项目检**：`数据表` 名 / `表头` 行 / `数据起始行` 三项是否与文件一致，
    然后**勾选唯一的索引列**（默认全部不勾 —— 不勾 = 这张表搜不到）。
    `数据类型` 全留 `String` 最稳（编号类如 `R-01` 选数值会丢前导字符）。
  - ⚠️ **NL2SQL / 聚合筛选是待实测能力，不是文档承诺能力**：官方文档**通篇没有**
    「自动转 SQL 做统计计算」的说法。确定性分层 ——
    索引列语义匹配返回整行（高，有原文）｜聚合/筛选/求和（低，**POC 实测前不得对客户承诺**）｜跨表 JOIN（不支持）。
    演示时可以拿"读回两行让大模型自己比"，但**口径必须说清是模型比、不是数据库算的**。
- **演示脚本要包含"答不出来"的题**。客户最担心 AI 胡说八道，
  **主动展示它说「资料里没有」比展示十个正确回答更能建立信任**；
  同时未命中的问题要落库（如 `unanswered`），让"该补什么资料"有数据依据。
- **长文档会被截断**，要在提示词里声明"仅基于所提供部分评分"，**不要假装检查了全文**
- **定时任务不属于任何用户**，必须遍历数据库里的活跃记录，不能靠"当前用户"
- **定时触发器要实测时区**，配错会变成凌晨推送
- **同一份输入两次处理结果要稳定**（评分类尤其重要），温度调到 0.2，还不够就把评分标准写机械化
- **平台数据库明文存储**：敏感信息用随机 ID（不要存学号/工号/身份证）、不存原始文档全文，
  真实身份映射留在甲方自己的系统里
- **别把"行业惯例"当成"硬标准"写进知识库**。先核实有没有统一标准——
  很多领域（如排版字号）根本没有国标，各机构写法都不同，**只能进数据库的"个别配置"字段**。
  写死在知识库的后果是：用 A 单位的要求去判 B 单位的东西。
- **Demo 阶段范围要钉死**：不影响"核心闭环跑通"的东西全部往后放（多 Agent、卡片、系统对接）

## 推荐的搭建顺序

```
D1 建数据库 + 导入测试数据            ← 纯准备
D2 建知识库                           ← 纯准备
D3 建边界守卫 + 被依赖最多的查询子工作流  ← 先立规矩，再接通数据源
D4 建核心闭环（建档 + 主流程 + 状态迁移）← 打通主干
D5 建最复杂的那条工作流
D6 建加分项工作流
D7 组装智能体 + 全量测试 + 定稿
```

**联调顺序的核心原则**：
1. **先建守卫**——它定义边界，边界没定后面全部可能返工
2. **再建被依赖最多的那个**——通常是一个查询子工作流，它不通后面会静默降级
3. **最复杂的放后面**

每条工作流用画布的「试运行」单测，不要通过对话调试（慢 10 倍）。
调试时优先怀疑五件事：**数组忘写 `[0]`、判空用了字符串而非长度、兜底查询漏了分类条件、
结束节点引用了分支内部才产出的变量、代码节点某个 `return` 少写了输出键**。
